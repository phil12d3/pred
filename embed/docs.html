1) What the embed Module Is For

The embed module creates and works with numeric representations of things. Those things can be words, documents, data series, observations, user records, or any other item you can describe with numbers or counts.

The module does not use a neural network. It uses statistical patterns, vector math, and matrix operations. That makes the system inspectable: an embedding is just an object with a list of numbers, and every function returns ordinary data.

You can use the module to:

  • Create empty, zero, random, or learned embeddings.
  • Normalize embeddings so they can be compared fairly.
  • Measure how similar or different two embeddings are.
  • Find the closest matches to a query embedding.
  • Average, merge, interpolate, expand, project, rotate, or orthogonalize embeddings.
  • Cluster a group of embeddings or compare two populations.
Important: an embedding is only as meaningful as the data used to build it. If every item is generated from exactly the same input, every item will look identical. For text terms, use term-specific context data such as co-occurrence, not one shared frequency map for every word.

2) Beginner Concepts and Terminology

Embedding: a list of numbers that represents an item. For example, the word "apple" might become a 12-number vector. Similar items should end up with similar vectors.
Vector: another name for a list of numbers. In this module, an embedding's values field is the vector.
Dimension: one position in the vector. A 4-dimensional embedding has four numeric values. A 12-dimensional embedding has twelve numeric values.
Magnitude: the length of a vector. A large magnitude means the numbers are collectively large. Many comparison methods are easier to interpret after embeddings are normalized to magnitude 1.
Normalization: rescaling values so embeddings can be compared fairly. L2 normalization changes a vector so its magnitude is 1, while keeping its direction.
Cosine similarity: a score based on direction. If two normalized embeddings point in the same direction, cosine is close to 1. If they point in unrelated directions, it is closer to 0. If they point opposite ways, it can be negative.
Distance: a measure of how far apart two embeddings are. Small distance means close. Large distance means different. Similarity and distance move in opposite directions.
Co-occurrence: when two terms appear near each other. In text embeddings, "apple" appearing near "fruit" and "sweet" gives the module context for what "apple" is related to.
Positional encoding: extra vector information that says where an item appears in a sequence. Without it, the same token embedding looks identical at position 0 and position 5. With it, the content can stay recognizable while the position becomes distinguishable.

3) Importing the Module

The main import file is embed.ns. It exposes five namespaces: core, learn, distance, ops, and utils.

embed = import("./embed.ns"); // Create an embedding. item = embed.core.create(4, "item_a"); // Learn an embedding from data. learned = embed.learn.fromFrequencies({"red": 3, "blue": 1}, 8); // Compare embeddings. score = embed.distance.similarity(item, learned, "cosine");
Runtime note: in the current NS runtime, functions with default-like behavior still need the full argument list in many places. Use null for optional arguments when needed, for example embed.core.create(8, null) or embed.learn.fromCoOccurrence(cooc, "apple", 12, null).

4) The Embedding Object Shape

Most functions either accept or return an embedding object. It has four fields:

{ dims: 4, values: [0.5, 0.2, 0.1, 0.8], id: "example_embedding", metadata: { label: "apple" } }
FieldMeaningBeginner explanation
dimsNumber of dimensions.This should match the number of items in values.
valuesArray of numbers.This is the actual vector. It is what math functions compare and transform.
idIdentifier string.A human or program-friendly name for the embedding.
metadataObject of extra fields.Use this to store labels, source terms, frequencies, classes, or other non-vector information.

Most functions return a new embedding-like object instead of changing the old one directly. In practice, assign the result back to a variable:

emb = embed.core.create(4, "demo"); emb = embed.core.set(emb, 0, 1); emb = embed.core.normalize(emb);

5) Choosing Dimensions

The number of dimensions controls how much room the embedding has to store patterns. More dimensions can represent more detail, but they also make vectors larger and may be harder to inspect.

  • 4 to 8 dimensions: useful for tiny examples, tests, and easy printing.
  • 12 to 32 dimensions: practical for small text or numeric demos.
  • 64 or more dimensions: useful when you have more terms, more contexts, or more complex data.

Dimensions are not named. Dimension 0 does not automatically mean "fruitness" or "temperature". The meaning emerges from the construction method and the data. If you need named, explainable fields, use ordinary feature objects instead of embeddings.

6) Which Namespace Should I Use?

The module is split into namespaces so you can find the right tool quickly. If you are new to embeddings, this section is the practical map.

A common full workflow uses all five namespaces:

// 1. Learn vectors from data. apple = embed.learn.fromCoOccurrence(cooc, "apple", 12, null); banana = embed.learn.fromCoOccurrence(cooc, "banana", 12, null); // 2. 7) Core Functions

The embed.core namespace contains basic embedding construction, inspection, and editing functions.

create(dimensions, seedId)
Purpose: Create a zero-filled embedding with the requested number of dimensions.
Pass in: dimensions as a number, and seedId as a string or null.
Returns: an embedding with values filled with zeros.
Use when: you want to manually set values one dimension at a time.
emb = embed.core.create(4, "manual"); // values are [0, 0, 0, 0]
set(embedding, index, value)
Purpose: Return a copy of an embedding with one dimension changed.
Pass in: an embedding, a zero-based index, and the new number.
Returns: an embedding with the updated value. Invalid indexes return the original embedding.
Use when: building vectors manually or adjusting one dimension.
at(embedding, index)
Purpose: Read one dimension from an embedding.
Pass in: an embedding and a zero-based index.
Returns: the number at that index, or 0 if the index is out of bounds.
magnitude(embedding)
Purpose: Compute the vector length, also called the L2 norm.
Pass in: an embedding.
Returns: a number. A zero embedding has magnitude 0. A normalized embedding usually has magnitude close to 1.
normalize(embedding)
Purpose: Scale an embedding so its magnitude is 1.
Pass in: an embedding with non-zero values.
Returns: a normalized embedding with the same dimensions, id, and metadata.
Use when: comparing direction with cosine similarity. Avoid normalizing all-zero vectors.
rescaleNorm(embedding)
Purpose: Rescale the smallest value to -1 and the largest value to 1.
Pass in: an embedding.
Returns: an embedding whose values are spread across the [-1, 1] range. If all values are equal, it returns zeros.
clamp(embedding)
Purpose: Limit each value so it cannot go below -1 or above 1.
Pass in: an embedding.
Returns: an embedding with the same shape and clipped values.
Example: 2.5 becomes 1, -2.5 becomes -1, and 0.5 stays 0.5.
stats(embedding)
Purpose: Summarize an embedding's values.
Pass in: an embedding.
Returns: {mean, variance, stddev, min, max, count}.
Use when: debugging whether values are too small, too large, all the same, or spread out.
copy(embedding)
Purpose: Duplicate an embedding.
Pass in: an embedding.
Returns: a new embedding object with copied values and an id ending in _copy.
withMetadata(embedding, key, value)
Purpose: Attach non-vector information to an embedding.
Pass in: an embedding, a string key, and any value.
Returns: an embedding with updated metadata.
Use when: storing labels such as term, frequency, source, or class.
zero(dimensions)
Purpose: Create an all-zero embedding.
Pass in: the number of dimensions.
Returns: an embedding with id like zero_... and all values set to 0.
random(dimensions, seedVal)
Purpose: Create a deterministic pseudo-random embedding with values in roughly [-1, 1].
Pass in: dimensions and a numeric seed.
Returns: an embedding with generated values.
Use when: creating toy examples or initial vectors. Do not treat random embeddings as meaningful until they are learned or transformed.

Internal math helpers in core.ns

The source file also contains abs(x), max(a, b), min(a, b), and sqrt(x). These are small helper functions used to support the module's math. They return ordinary numbers and are not usually the functions you reach for when working with embeddings. In normal application code, prefer the embedding-level functions above.

8) Learning Functions

The embed.learn namespace creates embeddings from observed data. This is where raw counts become vectors.

fromFrequencies(freqMap, dimensions)
Purpose: Turn a frequency or weight map into one embedding.
Pass in: an object whose keys are labels and whose values are numbers, plus the number of dimensions.
Returns: a normalized embedding.
How it works: it extracts numeric counts, computes statistics such as concentration and spread, then fills dimensions from weighted patterns.
Use when: one item is described by a distribution of counts. Do not call this with the same frequency map for every term unless you intentionally want identical embeddings.
freq = {"red": 5, "sweet": 3, "fruit": 4}; appleProfile = embed.learn.fromFrequencies(freq, 8);

How to think about frequency input

A frequency map describes one item. For example, if a product profile has counts for user actions, or a document has counts for themes, that whole map can become one embedding. The keys do not become labels in the returned object; they influence the numeric values.

The common mistake is using one global map to create many embeddings. If globalFreq is the same object every time, then fromFrequencies(globalFreq, 12) returns the same vector every time. To create different embeddings, each call needs different input.

fromCoOccurrence(cooccMatrix, term, dimensions, maxContextTerms)
Purpose: Build an embedding for one term from the terms that appear near it.
Pass in: a nested object, the target term string, dimensions, and a context limit or null.
Returns: a normalized embedding for the target term. If the term is missing or has no context, it returns a zero embedding.
Input shape: {"apple": {"fruit": 3, "sweet": 2}} means "apple appeared near fruit three times and sweet twice".
How it works: context terms are projected into sparse dimensions. Shared contexts land in shared dimensions, so terms with overlapping neighborhoods become more similar.
cooc = { "apple": {"fruit": 3, "sweet": 2, "pie": 1}, "banana": {"fruit": 2, "sweet": 1, "yellow": 3} }; apple = embed.learn.fromCoOccurrence(cooc, "apple", 12, null); banana = embed.learn.fromCoOccurrence(cooc, "banana", 12, null);

How to think about co-occurrence input

A co-occurrence matrix describes many terms at once, but each call still asks for one target term. This is the preferred beginner method for text because the data is easy to inspect. You can look at cooc["apple"] and see which contexts shaped the apple embedding.

The optional maxContextTerms argument limits how many context terms are used after sorting by count. Passing null lets the function use its default. A small limit focuses on strongest evidence. A larger limit includes more weak context.

fromCorpus(corpus, term, dimensions)
Purpose: Generate a corpus-derived embedding for a term by scanning document text.
Pass in: a corpus shaped like {docs: [...]}, a term string, and dimensions.
Returns: a normalized embedding with id "corpus_emb" and empty metadata.
Use when: you have raw documents and want the function to derive term frequency, document coverage, position, and nearby context evidence for you.

fromCorpus input shape

The function expects an object with a docs array. Each item in docs is usually a document string. Non-string values are converted with stringify, but plain strings are the intended input.

corpus = { docs: [ "apple fruit sweet", "banana fruit yellow", "orange citrus juice" ] }; apple = embed.learn.fromCorpus(corpus, "apple", 12);

What fromCorpus currently uses

The implementation now reads the document text and derives several pieces of evidence:

  • Term frequency: how many times the target term appears across all documents.
  • Document frequency: how many documents contain the target term at least once.
  • Average position: whether the term tends to appear earlier or later in matching documents.
  • Context diversity: how many distinct nearby words appear around the term.
  • Context density: how much local context evidence was collected relative to the whole corpus.
  • Nearby context terms: words within a small window around each target occurrence.

The first few dimensions store summary evidence such as frequency and coverage. Nearby context terms are then projected into dimensions using deterministic text-derived seeds. Terms that appear near similar words should therefore land closer together than terms with unrelated context.

Tokenization behavior: fromCorpus uses a simple built-in tokenizer. It keeps ASCII letters and numbers, splits on punctuation and whitespace, and lowercases ASCII uppercase letters. It is suitable for straightforward English-like tokens. It is not a full Unicode tokenizer.

When fromCorpus is useful

Use fromCorpus when you want the embedding module to do the basic text evidence gathering for you. It is a good choice for quick document experiments, small corpora, and situations where you do not want to separately build a co-occurrence matrix.

It is also useful when document-level coverage matters. For example, a term appearing once in every document and a term appearing many times in one document can produce different signatures because document frequency and total frequency are separate signals.

When to prefer fromCoOccurrence

Prefer fromCoOccurrence when you want full control over context collection. For example, you may want a different window size, sentence-bounded context, weighted context, stop-word filtering, or context from an external parser. fromCorpus uses a built-in local window and simple tokenization; fromCoOccurrence lets you provide exactly the context map you want.

Empty corpus behavior

If corpus.docs.count() is 0, or if the target term never appears, the function returns a zero embedding. A zero embedding means "no evidence found". It should not be treated as a meaningful semantic vector, and you should usually skip zero embeddings in similarity search.

Beginner mental model

Think of fromCorpus as "scan these documents, find this term, summarize how often it appears and what words surround it, then turn that evidence into a vector." It is not an LLM and it does not understand grammar, but it does use real corpus evidence rather than only a synthetic seed.

fromCorpus example comparison

corpus = { docs: [ "apple fruit red sweet", "apple pie sweet dessert", "engine road wheel car" ] }; apple = embed.learn.fromCorpus(corpus, "apple", 12); engine = embed.learn.fromCorpus(corpus, "engine", 12); // Apple and engine occur in different contexts, so their vectors should differ. distance = embed.distance.euclideanDistance(apple, engine);
learn(existingEmbedding, newData, learningRate)
Purpose: Move an existing embedding toward new numeric observations.
Pass in: an embedding, an array of numbers, and a learning rate from 0 to 1.
Returns: a normalized embedding with id ending in _learned.
How learning rate works: 0 keeps the old vector. 1 uses the new values as strongly as possible. Values like 0.1 update slowly; values like 0.7 update quickly.
base = embed.core.create(4, "profile"); base = embed.core.set(base, 0, 0.2); base = embed.core.set(base, 1, 0.2); base = embed.core.set(base, 2, 0.2); base = embed.core.set(base, 3, 0.2); updated = embed.learn.learn(base, [0.9, 0.4, 0.1, 0.7], 0.3);

9) Distance and Similarity Functions

The embed.distance namespace compares embeddings. Some functions return similarity, where higher means closer. Other functions return distance, where lower means closer.

Similarity versus distance: similarity answers "how alike are these?" Distance answers "how far apart are these?" A similarity of 1 is very close. A distance of 0 is identical.
FunctionPass inReturnsUse when
cosineSimilarity(emb1, emb2)Two same-dimension embeddings.Raw cosine, usually from -1 to 1.You care about direction or pattern, not magnitude.
euclideanDistance(emb1, emb2)Two same-dimension embeddings.L2 distance number.You want straight-line distance between vectors.
manhattanDistance(emb1, emb2)Two same-dimension embeddings.Sum of absolute differences.You want total per-dimension movement.
chebyshevDistance(emb1, emb2)Two same-dimension embeddings.Largest single-dimension difference.You care about the worst mismatch.
minkowskiDistance(emb1, emb2, p)Two embeddings and power p.Generalized distance.You need a tunable distance metric.
hammingDistance(emb1, emb2, threshold)Two embeddings and a difference threshold.Count of dimensions that differ by more than the threshold.You want to count significant dimension changes.
wassersteinDistance(emb1, emb2)Two same-dimension embeddings.Average distance between sorted value distributions.You care about value distribution more than dimension position.

How to read cosine scores

Raw cosine scoreBeginner interpretation
Close to 1The vectors point in almost the same direction. They have a very similar pattern.
Around 0.5There is some overlap, but it is not a very strong match.
Around 0The vectors are mostly unrelated in this embedding space.
Below 0The vectors point in opposite directions. This is possible for signed vectors; sparse positive co-occurrence vectors usually produce fewer negative scores.

How to choose a metric

Use cosine when you care about pattern similarity. Use Euclidean when you want a literal distance through vector space. Use Manhattan when many small differences should add up. Use Chebyshev when one large mismatch matters more than the total. Use Wasserstein when the order of dimensions matters less than the distribution of values.

similarity(emb1, emb2, metric)
Purpose: General wrapper for similarity scoring.
Pass in: two embeddings and a metric string such as "cosine", "euclidean", or "manhattan".
Returns: for "cosine", raw cosine. For distance metrics, 1 / (1 + distance), so closer items get scores nearer 1.
Beginner tip: use "cosine" for normalized learned embeddings and use Euclidean distance when you want a more concrete "how far apart" number.
findMostSimilar(queryEmbedding, embeddingList, topK, metric)
Purpose: Find the closest embeddings to a query.
Pass in: a query embedding, an array of candidate embeddings, the number of results to return, and a metric string.
Returns: an array of objects shaped like {index, embedding, similarity}, sorted by highest similarity first.
Use when: implementing nearest-neighbor search, recommendations, or "show me similar items" behavior.
matches = embed.distance.findMostSimilar(query, allEmbeddings, 5, "cosine"); for (i = 0; i < matches.count(); i = i + 1) { print(matches[i].embedding.metadata.label); print(matches[i].similarity); }

10) Operations for Combining Embeddings

The embed.ops namespace transforms embeddings. These functions usually return normalized embeddings, so the output is ready for comparison.

add(emb1, emb2)
Adds values dimension by dimension. Requires matching dimensions. Returns a normalized embedding.
subtract(emb1, emb2)
Subtracts emb2 from emb1 dimension by dimension. Useful for difference vectors. If the result is all zero, normalization may not be meaningful.
multiply(embedding, scalar)
Scales every value by a number, then normalizes. Because it normalizes afterward, multiplying by larger numbers changes direction only if signs or zeros are involved.
hadamard(emb1, emb2)
Multiplies two embeddings dimension by dimension. Useful when you want dimensions to reinforce each other only where both embeddings have strong values.
average(embeddings)
Averages an array of embeddings. Returns a group summary with the same dimensions as the first embedding.
weightedAverage(embeddings, weights)
Like average, but each embedding can contribute more or less. If weights are missing or invalid, it falls back to a plain average.
merge(embeddings, targetDims)
Combines multiple embeddings, then projects the combined values into targetDims. Useful for document embeddings from word embeddings.
interpolate(emb1, emb2, alpha)
Blends between two embeddings. alpha = 0 stays at emb1; alpha = 1 reaches emb2; 0.5 is halfway.
project(embedding, targetDims)
Reduces dimensions by keeping high-variance dimensions. Use when you need a smaller vector.
expand(embedding, targetDims)
Increases dimensions by keeping existing values and adding small deterministic noise based on spread. Use when an API requires a larger dimension count.
rotate(embedding, rotationFactor)
Cyclically shifts values. rotationFactor is clamped from 0 to 1. Useful for synthetic transformations and tests.
positionalEncoding(position, dimensions, maxPosition)
Creates a standalone position vector. position is the zero-based sequence index, dimensions is the vector size, and maxPosition controls the broad position range. Returns a normalized embedding with metadata containing the position.
addPositionalEncoding(embedding, position, strength)
Blends position information into an existing embedding. strength ranges from 0 to 1; lower values preserve content more strongly, higher values make position matter more. Returns a normalized embedding with position metadata.
analogy(aEmbedding, bEmbedding, cEmbedding)
Runs vector arithmetic in the form a - b + c, normalizes the result, and returns a new embedding. Use this as a relationship query: compare the returned vector with known embeddings using nearest-neighbor search. It is exploratory, not symbolic reasoning.
compose(baseEmbedding, additions, removals)
Builds a flexible query vector from one base embedding, an array of embeddings to add, and an array of embeddings to remove. Returns a normalized embedding. Use this when a - b + c is too narrow.
moveAwayFrom(sourceEmbedding, avoidEmbedding, strength)
Moves a source embedding away from an unwanted concept by subtracting the avoid vector with a strength value. Returns a normalized embedding. Use this for "similar to this, but less like that" queries.
applyDirection(sourceEmbedding, directionEmbedding, strength)
Applies a reusable direction to a source embedding. Returns a normalized embedding. Use this after creating a direction with subtract, centroidDirection, or another operation.
centroidDirection(fromGroup, toGroup)
Computes the direction from the average of one group to the average of another group. Returns a normalized direction embedding. Use this for group-level shifts, such as moving from fruit-like terms toward vehicle-like terms.
contrast(aEmbedding, bEmbedding, candidates, k)
Builds the difference direction a - b, compares candidate embeddings against that direction, and returns the top k result objects. Use this to ask which candidates most express the contrast between two embeddings.
sequenceEmbedding(embeddings, positionalStrength)
Summarizes an ordered list of embeddings. Each item is blended with a position signal before the final average, so [apple, banana] can differ from [banana, apple]. Returns a normalized embedding with metadata containing sequence length and position strength.
orthogonalize(embedding, referenceEmbedding)
Removes correlation with a reference embedding. Use when you want to reduce overlap with a known direction or concept.
// Build a document embedding from word embeddings. docEmbeddings = [apple, fruit, sweet]; document = embed.ops.merge(docEmbeddings, 12); // Blend two profiles. blend = embed.ops.interpolate(profileA, profileB, 0.25);

Using embeddings as queries

The analogy function is useful when you want to create a new query vector from a relationship. For example, apple - fruit + engine asks the embedding space for something that keeps some apple-specific direction, removes some fruit-like direction, and adds engine-like direction. The module cannot guarantee a perfect human analogy, but the resulting vector can be searched against known embeddings.

query = embed.ops.analogy(apple, fruit, engine); matches = embed.distance.findMostSimilar(query, allTerms, 5, "cosine");

A good way to read analogy output is to compare before and after. First search with the original embedding, then search with the arithmetic query. The before list shows where the original term already lives. The after list shows where the arithmetic moved the query.

before = embed.distance.findMostSimilar(apple, allTerms, 4, "cosine"); query = embed.ops.analogy(apple, fruit, engine); after = embed.distance.findMostSimilar(query, allTerms, 4, "cosine"); appleToQuery = embed.distance.similarity(apple, query, "cosine"); engineToQuery = embed.distance.similarity(engine, query, "cosine");

In beginner terms, the subtraction part is a direction removal. It does not delete the word "fruit" from a sentence. It reduces the vector components that the current embedding space associates with the second input. The addition part then pushes the vector toward the third input. This only works well when the inputs were created by the same learning method, with the same dimensions, from data that contains enough repeated patterns.

Flexible query arithmetic

analogy is intentionally specific: it always means a - b + c. The flexible helpers cover related tasks that come up when you want to use embeddings as query-building blocks.

// More flexible than analogy: query = embed.ops.compose(apple, [engine, road], [fruit]); matches = embed.distance.findMostSimilar(query, allTerms, 5, "cosine"); // Similar to apple, but less fruit-like: lessFruit = embed.ops.moveAwayFrom(apple, fruit, 0.60); // Learn a reusable group direction, then apply it: vehicleDirection = embed.ops.centroidDirection( [apple, banana, orange], [car, truck, engine] ); directedApple = embed.ops.applyDirection(apple, vehicleDirection, 0.75); // Find terms aligned with the difference between two concepts: contrastMatches = embed.ops.contrast(engine, fruit, allTerms, 3);

These functions still do vector math, not symbolic reasoning. Their value is that the function names describe the query intent: compose a query, move away from a concept, apply a learned direction, compute a group-to-group direction, or inspect a contrast. That is clearer than scattering manual arithmetic through examples.

How each query arithmetic helper changes a vector

All of these helpers expect embeddings from the same embedding space: same dimensions, same construction method, and comparable source data. Most return a new normalized embedding, which means the output is ready for cosine similarity or nearest-neighbor search.

analogy(aEmbedding, bEmbedding, cEmbedding)
Pass in: three embeddings with matching dimensions.
Math: a - b + c.
How it changes the embedding: starts at a, reduces the direction shared with b, then pushes the result toward c.
Returns: a normalized query embedding. Search with it using findMostSimilar.
compose(baseEmbedding, additions, removals)
Pass in: a base embedding, an array of embeddings to add, and an array of embeddings to remove. Empty arrays are fine.
Math: base + every addition - every removal.
How it changes the embedding: keeps the base as the anchor, pulls the vector toward all additions, and pushes it away from all removals.
Returns: a normalized embedding with metadata recording how many additions and removals were applied.
moveAwayFrom(sourceEmbedding, avoidEmbedding, strength)
Pass in: a source embedding, an avoid embedding, and a strength number. If strength is missing, it uses 0.5.
Math: source - avoid * strength before normalization.
How it changes the embedding: keeps the query related to the source, but reduces alignment with the avoid concept. Higher strength pushes harder away.
Returns: a normalized embedding with strength metadata.
centroidDirection(fromGroup, toGroup)
Pass in: two arrays of embeddings. The first is the source group; the second is the target group.
Math: average(toGroup) - average(fromGroup).
How it changes the embedding: this does not move a single source item by itself. It creates a reusable direction vector that describes how to move from one group center toward another group center.
Returns: a normalized direction embedding with metadata containing the group counts.
applyDirection(sourceEmbedding, directionEmbedding, strength)
Pass in: a source embedding, a direction embedding, and a strength number. If strength is missing, it uses 1.
Math: source + direction * strength before normalization.
How it changes the embedding: moves the source along a reusable direction. This is useful after centroidDirection, or after creating a direction with subtract.
Returns: a normalized embedding with strength metadata.
contrast(aEmbedding, bEmbedding, candidates, k)
Pass in: two embeddings to define a contrast, a candidate embedding array, and the number of results to return.
Math: creates the direction a - b, then scores candidates by cosine alignment to that direction.
How it changes the embedding: it does not return one transformed embedding. Instead, it ranks candidates by how strongly they point in the same direction as the contrast.
Returns: an array of result objects shaped like {embedding, similarity, index}.

Summarizing ordered content

A normal average treats [apple, banana, orange] and [orange, banana, apple] as the same bag of items. sequenceEmbedding keeps a lightweight order signal by adding positional encoding to each item before summarizing. Use it for short sequences, phrase-like comparisons, ordered events, or any situation where order should matter but you still want one vector at the end.

phraseA = embed.ops.sequenceEmbedding([apple, banana, orange], 0.20); phraseB = embed.ops.sequenceEmbedding([orange, banana, apple], 0.20); orderScore = embed.distance.similarity(phraseA, phraseB, "cosine");

When operations can be misleading

Operations are mathematical transformations, not guarantees of meaning. Adding two word embeddings can be useful, but the result is not automatically a perfect phrase embedding. Subtracting two identical embeddings produces a zero vector, which cannot be normalized into a meaningful direction. Interpolation is useful for blending two profiles, but the halfway point is only meaningful if both inputs live in the same embedding space.

How positional encoding works in this module

Classic transformer models often use sine and cosine waves for positional encoding. The NS runtime used here does not expose trigonometric functions, so this module uses deterministic multi-period triangle-wave features instead. The purpose is the same: every position gets a stable vector pattern, and nearby or repeated positions can be distinguished.

Use positionalEncoding when you want the position vector by itself. Use addPositionalEncoding when you already have a content embedding and want to blend sequence position into it.

token = embed.core.create(8, "token"); // ...set and normalize token... tokenAt0 = embed.ops.addPositionalEncoding(token, 0, 0.25); tokenAt5 = embed.ops.addPositionalEncoding(token, 5, 0.25); // Same content, different sequence positions. sim = embed.distance.similarity(tokenAt0, tokenAt5, "cosine");

The strength value controls the tradeoff. A value like 0.1 makes position subtle. A value like 0.5 makes position much more prominent. For most text-like workflows, start around 0.2 to 0.3.

11) Utility Functions

The embed.utils namespace contains functions for working with groups of embeddings.

normalizeAll(embeddings)
Pass in: an array of embeddings. Returns: a new array where each embedding has been normalized and clamped.
createIndex(embeddings, keyField)
Pass in: embeddings and a metadata field name, or null to use ids. Returns: an object mapping keys to embeddings. Use this for fast lookup by label.
approximateNearestNeighbor(queryEmbedding, embeddingList, k, metric)
Pass in: query, candidates, result count, and metric. Returns: result objects with {embedding, similarity, index}. This uses inline cosine-style scoring.
summarize(embeddings)
Pass in: an array of embeddings. Returns: one normalized embedding that summarizes the group using positional weights.
diversity(embeddings)
Pass in: an array of embeddings. Returns: average pairwise Euclidean distance. Higher means the population is more spread out.
cluster(embeddings, maxDist, metric)
Pass in: embeddings, a distance threshold, and a metric string. Returns: an array of clusters, where each cluster is an array of embeddings. Lower thresholds make smaller, stricter clusters.
centroid(embeddingCluster)
Pass in: one cluster, meaning an array of embeddings. Returns: a normalized average embedding representing the center of that cluster.
filterBySimilarity(embeddings, queryEmbedding, minSimilarity, metric)
Pass in: embeddings, a query, minimum similarity, and metric. Returns: only embeddings whose similarity is at least the threshold.
similarityMatrix(embeddings, metric)
Pass in: an array of embeddings and a metric string such as "cosine", "euclidean", or "manhattan". Returns: a two-dimensional array where matrix[i][j] is the similarity between embeddings[i] and embeddings[j]. Use this to print a comparison table, inspect clusters, spot outliers, or debug whether every vector is accidentally too similar.
batchTransform(embeddings, transformFunc)
Pass in: embeddings and a function. Returns: transformed embeddings. Use this to apply the same operation to many embeddings.
toMatrix(embeddings)
Pass in: embeddings. Returns: a two-dimensional array of only the numeric values. Useful when a matrix-like API needs rows of numbers.
comparePopulations(pop1, pop2)
Pass in: two arrays of embeddings. Returns: {similarity, diversity1, diversity2}. Use this to compare two groups rather than two individual items.
matrix = embed.utils.similarityMatrix(allTerms, "cosine"); // Read as: similarity between allTerms[0] and allTerms[2]. score = matrix[0][2];

12) Text Embedding Walkthrough

This walkthrough explains the text embedding process in beginner terms. The important idea is that a word embedding should be built from that word's own context, not from a shared global summary.

Step 1: Start with tokenized documents

A token is a cleaned word-like piece of text. In the example below, punctuation has already been removed and every word is lowercase.

docs = [ ["apple", "fruit", "red", "sweet"], ["banana", "fruit", "yellow", "sweet"], ["engine", "road", "wheel", "car"] ];

Step 2: Build a co-occurrence matrix

For each target word, count nearby words. A small window makes local context matter more. In a four-word document, a window of 1 means each word only sees its immediate neighbors. A window of 2 sees a little farther.

cooc = { "apple": {"fruit": 1}, "fruit": {"apple": 1, "red": 1, "banana": 1, "yellow": 1}, "banana": {"fruit": 1}, "car": {"wheel": 1} };

Step 3: Learn one embedding per target term

Each term gets a vector based on its own row in the matrix. If two terms share context, their vectors should be closer. If they have unrelated context, they should be farther apart.

apple = embed.learn.fromCoOccurrence(cooc, "apple", 12, null); banana = embed.learn.fromCoOccurrence(cooc, "banana", 12, null); car = embed.learn.fromCoOccurrence(cooc, "car", 12, null);

Step 4: Compare terms

Now cosine similarity has something meaningful to compare. Apple and banana both connect to fruit, so they should be closer than apple and car.

fruitScore = embed.distance.similarity(apple, banana, "cosine"); vehicleScore = embed.distance.similarity(apple, car, "cosine");

Step 5: Attach labels for display

The vector itself is just numbers. Store labels in metadata so search results can be printed clearly.

apple = embed.core.withMetadata(apple, "term", "apple"); banana = embed.core.withMetadata(banana, "term", "banana"); car = embed.core.withMetadata(car, "term", "car");

13) Common Workflows

Workflow A: Build a manual embedding

embed = import("./embed.ns"); profile = embed.core.create(4, "profile_a"); profile = embed.core.set(profile, 0, 0.9); profile = embed.core.set(profile, 1, 0.4); profile = embed.core.set(profile, 2, 0.1); profile = embed.core.set(profile, 3, 0.7); profile = embed.core.normalize(profile);

Workflow B: Create text term embeddings from co-occurrence

For text, a good beginner pattern is: tokenize text, build a co-occurrence matrix, then call fromCoOccurrence once per term.

cooc = { "apple": {"fruit": 3, "sweet": 2, "pie": 1}, "banana": {"fruit": 2, "yellow": 3, "sweet": 1}, "car": {"road": 3, "engine": 2, "wheel": 2} }; apple = embed.learn.fromCoOccurrence(cooc, "apple", 12, null); banana = embed.learn.fromCoOccurrence(cooc, "banana", 12, null); car = embed.learn.fromCoOccurrence(cooc, "car", 12, null); appleBanana = embed.distance.similarity(apple, banana, "cosine"); appleCar = embed.distance.similarity(apple, car, "cosine");

Workflow C: Find similar items

items = [apple, banana, car]; matches = embed.distance.findMostSimilar(apple, items, 3, "cosine"); // matches[0] will usually be apple itself if apple is included in items. // For search results, skip the query item when displaying output.

Workflow D: Build a document embedding from word embeddings

wordEmbeddings = [apple, banana, fruit]; doc = embed.ops.merge(wordEmbeddings, 12); doc = embed.core.withMetadata(doc, "title", "fruit document");

Workflow E: Combine text meaning with position

Use a text embedding for meaning, then blend positional encoding into it. This lets the same word at different sequence positions become distinguishable while preserving the semantic signal.

apple = embed.learn.fromCorpus(corpus, "apple", 64); banana = embed.learn.fromCorpus(corpus, "banana", 64); car = embed.learn.fromCorpus(corpus, "car", 64); // Same position: semantic ordering should remain intact. appleAt2 = embed.ops.addPositionalEncoding(apple, 2, 0.20); bananaAt2 = embed.ops.addPositionalEncoding(banana, 2, 0.20); carAt2 = embed.ops.addPositionalEncoding(car, 2, 0.20); related = embed.distance.similarity(appleAt2, bananaAt2, "cosine"); unrelated = embed.distance.similarity(appleAt2, carAt2, "cosine"); // Different positions: same content is no longer identical. appleAt0 = embed.ops.addPositionalEncoding(apple, 0, 0.20); appleAt5 = embed.ops.addPositionalEncoding(apple, 5, 0.20);

The example file examples/text_with_positions.ns prints these comparisons and checks that related meanings remain closer than unrelated meanings after position is added.

Workflow F: Inspect and query a generated embedding set

After you have a list of term embeddings, use similarityMatrix to see the whole comparison landscape, analogy and the flexible query arithmetic helpers to create relationship queries, and sequenceEmbedding to compare ordered sequences. The example file examples/embedding_tools.ns demonstrates these tools together.

matrix = embed.utils.similarityMatrix(embeddingList, "cosine"); query = embed.ops.analogy(apple, fruit, engine); matches = embed.distance.findMostSimilar(query, embeddingList, 4, "cosine"); composed = embed.ops.compose(apple, [engine, road], [fruit]); lessFruit = embed.ops.moveAwayFrom(apple, fruit, 0.60); vehicleDirection = embed.ops.centroidDirection( [apple, banana, orange], [car, truck, engine] ); directedApple = embed.ops.applyDirection(apple, vehicleDirection, 0.75); contrastMatches = embed.ops.contrast(engine, fruit, embeddingList, 3); fruitSequence = embed.ops.sequenceEmbedding([apple, banana, orange], 0.20); vehicleSequence = embed.ops.sequenceEmbedding([car, truck, engine], 0.20); sequenceScore = embed.distance.similarity(fruitSequence, vehicleSequence, "cosine");

14) Interpreting Results and Avoiding Mistakes

Similarity numbers are not universal truth

A similarity score depends on the data, the dimensions, and the construction function. A score of 0.80 in one corpus does not necessarily mean the same thing as 0.80 in another corpus.

Identical inputs produce identical embeddings

If you call fromFrequencies(theSameMap, 12) for every word, every word receives the same embedding. To create one embedding per term, use term-specific input such as each term's own co-occurrence context.

Small corpora can be noisy

With only a few documents, scores can be shaped by accidental context overlap or hash collisions. Treat examples as demonstrations. For more stable semantic behavior, use more repeated context patterns and enough dimensions for the number of distinct contexts.

Normalize before comparing direction

Cosine similarity is easiest to interpret when embeddings are normalized. Most learning and ops functions already normalize their outputs. If you manually build vectors with create and set, call normalize before comparing them.

Watch for zero vectors

A zero vector has no direction. Some normalization operations cannot normalize a zero matrix. Missing co-occurrence returns a zero embedding to signal "no evidence". Do not treat that as a meaningful semantic vector.

Use metadata for display labels

The vector values do not remember what item they came from unless you store it. Use withMetadata to attach labels such as term, documentId, or category.

Choose dimensions based on your data

If many unrelated items look too similar, try increasing dimensions or improving the input features. If results are unstable or hard to inspect, try a smaller dimension count while debugging.

Use the same construction method for comparable embeddings

Only compare embeddings that live in the same space. An embedding from fromCoOccurrence and an embedding from unrelated manual values may have the same number of dimensions, but the dimensions were created for different reasons. Same shape does not always mean same meaning.

Document your thresholds

If you decide that similarity above 0.65 counts as a match, write down how you chose that threshold. Thresholds should usually be tuned by looking at real examples from your own data.

Prefer examples over abstract confidence

When validating an embedding setup, print nearest neighbors for several known terms. If "apple" is near fruit words and "car" is near vehicle words, the setup is learning useful structure. If every item is near every other item, the input is too broad or the vectors are too compressed.
