store Documentation

A small in-memory container for forecasts, drift reports, evaluation summaries, and any other structured analysis artifact.

Start with examples/demo.ns and examples/bundle_roundtrip.ns.

What This Module Is For

store is a lightweight registry. It gives a name to an analysis object and keeps that object available for later steps in the same process. This is useful when you have several intermediate products such as a normalized history, a forecast, an evaluation summary, and a drift report, and you want a simple place to keep them organized.

This module is deliberately small. It is still an in-process registry first, but it can now save values and whole store snapshots to disk and load them back later. Think of it as an indexed shelf with optional local persistence, not a database.

The current internal shape is {entries: [{key, value}, ...]}. Order matters. The module preserves insertion order so reports and demos stay predictable.

Data Model

Field Meaning
entries An ordered array of objects, each with key and value.
key The name used to look up the stored artifact later.
value Any structured object, row, history, report, or summary you want to keep.

Conceptually, this behaves like a map with stable ordering. Unlike a raw object map, the ordering is explicit because it is stored as an array of entries.

Functions

create()

Use it for: creating an empty store.
Output: {entries: []}.
What it does: establishes the standard container shape used by every other function.

put(store, key, value)

Use it for: adding a new artifact or replacing an existing one.
Input: a store object, a key string, and any value.
Output: a new store object.
What it does: walks through the entries, replaces the entry if the key already exists, otherwise appends a new entry.
s = store.create(); s = store.put(s, "history", {rows: 4, streams: 3}); s = store.put(s, "forecast", {A: 7, B: "active"}); // s.entries = [ // {key: "history", value: {rows: 4, streams: 3}}, // {key: "forecast", value: {A: 7, B: "active"}} // ]

The practical effect is immutability by replacement. The function returns a fresh container instead of editing the prior one in place. That makes step-by-step workflows easier to reason about.

lookup(store, key)

Use it for: retrieving one stored value.
Input: a store and a key.
Output: the stored value, or null if the key is missing.
What it does: performs a linear scan over the ordered entries until it finds a matching key.

This is the basic read operation. Because the store is implemented as an ordered array, lookup cost grows with the number of items. That is fine for small analysis workflows, which is the intended use case.

has(store, key)

Use it for: checking whether an item exists before reading or replacing it.
Output: true or false.

drop(store, key)

Use it for: removing one entry by name.
Output: a new store without that key.
What it does: copies every entry except the matching one.
s = store.drop(s, "history"); // If "history" existed, it is gone. // All other entries keep their original order.

list(store)

Use it for: seeing which artifacts are stored and in what order.
Output: an array of keys.

snapshot(store)

Use it for: copying the store into a plain transferable object.
Output: another store-shaped object.
What it does: copies the entries array into a fresh container.

restore(snapshot)

Use it for: rebuilding a store from a snapshot object.
Output: a valid store object.

snapshot() and restore() form a round-trip pair. They are useful when a workflow wants to pass store contents between modules without exposing the original live store object.

bundle(name, payload, metadata)

Use it for: grouping one result with descriptive context.
Output: {name, payload, metadata, kind:"analysis.bundle"}.
What it does: packages a result with a human-readable name and optional metadata such as source, date, or scenario label.
artifact = store.bundle( "baseline-forecast", {A: 7, B: "active"}, {createdBy: "demo", horizon: 1} ); // artifact.kind = "analysis.bundle"

pack(value) and unpack(value)

Use it for: marking a value as ready to move into or out of the store interface.
Current behavior: both functions return the value unchanged.

These functions exist as extension points. Right now they are identity operations, which means no encoding or structural rewrite is applied. In a future version they could become a place to standardize serialization rules.

saveFile(path, value)

Use it for: saving one value to disk.
Input: a file path and any store-compatible value.
Output: {path, saved}.
What it does: packs the value and writes it through the runtime's compressed file format.
result = store.saveFile("./tmp/forecast.bin", { forecast: {A: 12, B: "idle"}, notes: ["baseline", "saved to disk"] }); // result = {path: "./tmp/forecast.bin", saved: true}

This is persistence for arbitrary analysis values, not just whole store objects. The saved file is meant to be loaded back through loadFile().

loadFile(path)

Use it for: restoring one previously saved value from disk.
Input: a file path created by saveFile().
Output: the restored value.
loaded = store.loadFile("./tmp/forecast.bin"); // loaded.forecast.A = 12 // loaded.notes[1] = "saved to disk"

The structural effect is a round trip: nested objects, arrays, strings, and numbers come back in the same shape they had before saving.

saveStore(store, path)

Use it for: saving a whole store snapshot to disk.
Output: the same result shape as saveFile().
What it does: snapshots the current store and persists that snapshot as one file.

loadStore(path)

Use it for: restoring a previously saved store file.
Output: a live store object with entries.
What it does: loads the saved snapshot and passes it back through restore().

Example Workflow

store = import("./store.ns").store; s = store.create(); s = store.put(s, "history", {rows: 4, streams: 3}); s = store.put(s, "forecast", {A: 7, B: "active"}); s = store.put(s, "drift", {flagged: 1, score: 0.86}); keys = store.list(s); forecast = store.lookup(s, "forecast"); snapshot = store.snapshot(s); restored = store.restore(snapshot);

This shows the module’s role clearly: it does not analyze the objects, it organizes them. That separation is useful. Prediction modules make the artifacts. The store keeps them named and retrievable.

store.saveStore(s, "./tmp/analysis_store.bin"); reloaded = store.loadStore("./tmp/analysis_store.bin"); // reloaded.entries contains the same named artifacts as s.

With persistence added, the same organized artifact set can now survive beyond one script run.

When To Use It

  • Use store when one script creates several named results and you want to pass them around consistently.
  • Use bundle() when one result needs attached metadata.
  • Use saveFile() or saveStore() when those results need to survive after the script exits.
  • Do not use this module as a substitute for a database. It is intentionally simple local persistence.
