Overview

The module has two related search tools. Differential evolution searches for the best numeric parameter vector. Symbolic algorithm discovery searches for a small expression tree made from variables, constants, and operators. It includes an evolutionary strategy for open-ended expression search and a typed beam strategy for readable decision-rule induction. Both tools use the same idea: generate candidates, score them with a fitness function, keep better candidates, and repeat.

Use parameter optimisation when you already know the model shape and need to fit its numeric settings. Use algorithm discovery when you do not know the exact rule or formula and want the module to search for one.

TaskUseCandidate shapeFitness receives
Calibrate a model, policy, controller, simulator, or forecast genetic.de.optimize Array of numbers, for example [base, trend, promoLift] fitness(values, ctx)
Score a whole population in one call for heavier workloads genetic.de.optimizeBatch Array of candidate arrays batchFitness(candidateRows, ctx)
Discover a readable formula or decision rule genetic.discovery.evolve or direct import("./src/discover.ns") Expression tree fitness(program, tools, ctx)

Importing the Module

genetic = import("./genetic.ns");

The umbrella module exports:

  • genetic.de: numeric differential evolution.
  • genetic.discovery: symbolic expression discovery.
  • genetic.vectors: dense vector helpers used by the optimiser.
  • genetic.utils: deterministic random and scoring helpers.
  • genetic.run: a unified dispatcher for simple callers.

Parameter Optimisation

Parameter optimisation fits numbers. You define a candidate vector, bounds for each number, and a fitness function that returns a score. Lower score is better by default.

Demand Forecast Calibration

Suppose you use this compact forecast model: 

forecast = base + trend * week + promoLift * promo + priceSensitivity * (price - 10)

The structure is fixed. The unknowns are base, trend, promoLift, and priceSensitivity. Differential evolution searches those four values. 

genetic = import("./genetic.ns");

rows = [
    {week: 1, price: 10.0, promo: 0, sales: 121},
    {week: 2, price: 10.2, promo: 0, sales: 123},
    {week: 3, price: 9.8, promo: 1, sales: 148},
    {week: 4, price: 10.4, promo: 0, sales: 124}
];

predictSales = func(params, row) {
    base = params[0];
    trend = params[1];
    promoLift = params[2];
    priceSensitivity = params[3];
    return base + (trend * row.week) + (promoLift * row.promo) + (priceSensitivity * (row.price - 10));
};

fitness = func(values, ctx) {
    totalAbsError = 0;
    for (i = 0; i < rows.count(); i = i + 1) {
        predicted = predictSales(values, rows[i]);
        diff = predicted - rows[i].sales;
        if (diff < 0) diff = 0 - diff;
        totalAbsError = totalAbsError + diff;
    }
    return totalAbsError / rows.count();
};

result = genetic.de.optimize(fitness, [
    {min: 80, max: 160},
    {min: -2, max: 6},
    {min: 0, max: 60},
    {min: -80, max: 20}
], {
    populationSize: 48,
    generations: 120,
    mutationFactor: 0.75,
    crossoverRate: 0.9,
    seed: 23,
    threads: 4
});

printline("Mean absolute error: ", stringify(result.best.score));
printline("Best parameters: ", stringify(result.best.values));

Bounds

Bounds can be objects or two-item arrays:

bounds = [
    {min: 0, max: 100},
    [-10, 10]
];

Bounds are important. Wide bounds let the optimiser explore, but they also make the search harder. Prefer ranges that are broad enough to contain good answers but narrow enough to exclude impossible values.

Fitness Function Design

A fitness function should turn a candidate into one number. That number should reflect what you actually want. Common choices are:

  • Mean absolute error for forecasts and calibration.
  • Penalty-weighted cost for operations or scheduling.
  • Negative profit when using mode: "minimize", or profit with mode: "maximize".
  • Error plus constraint penalties when candidates can violate rules.
fitness = func(values, ctx) {
    cost = simulate(values);
    penalty = 0;
    if (values[0] < values[1]) penalty = penalty + 1000;
    return cost + penalty;
};

Differential Evolution Theory

Differential evolution is a population-based optimiser. Instead of keeping one current answer, it keeps a population of possible answers. Each answer is a vector of numbers. In each generation, the optimiser tries to improve every candidate by combining information from other candidates.

The Core Loop

  1. Create an initial population of random vectors inside the bounds.
  2. Score each vector with the fitness function.
  3. For each target vector, pick three distinct vectors from the population.
  4. Create a mutant vector: a + mutationFactor * (b - c).
  5. Cross the mutant with the target vector to create a trial vector.
  6. Score the trial vector.
  7. If the trial is better, replace the target. Otherwise keep the target.
  8. Repeat for the configured number of generations.

Why It Works

The difference vector (b - c) captures a direction and scale already present in the population. If the population has candidates spread around useful areas, these difference vectors become practical search steps. The method does not require gradients, derivatives, or a smooth objective. That makes it useful for simulations, forecasts, policy rules, and other systems where the score is available but the mathematical derivative is not.

Exploration and Exploitation

mutationFactor controls step size. Larger values explore more aggressively. Smaller values refine locally. crossoverRate controls how much of the mutant enters the trial candidate. Higher crossover mixes more new information into each trial. Population size controls diversity. More population means more search coverage, but more fitness calls.

Batch Fitness and Acceleration

Fitness scoring is usually the expensive part. optimizeBatch lets you score the whole population in one call: 

batchFitness = func(candidateRows, ctx) {
    scores = [];
    for (c = 0; c < candidateRows.count(); c = c + 1) {
        params = candidateRows[c];
        scores.add(scoreParams(params));
    }
    return scores;
};

result = genetic.de.optimizeBatch(batchFitness, bounds, {
    populationSize: 64,
    generations: 100,
    threads: 8
});

The module passes ctx.threads through to your fitness function. The current ns scripts do not create worker threads themselves, but the value is available for callers or runtimes that can parallelize scoring. The batch path also returns candidates as dense rows, which is the right shape for matrix or GPU-backed evaluation.

Algorithm Discovery

Algorithm discovery searches expression trees. A tree can contain variables, constants, and operators. The module generates candidate trees, runs them against your data, and keeps trees with better fitness.

Use the default evolutionary strategy for open-ended formula discovery. Use searchStrategy: "beam" for decision-rule problems where you want typed predicates such as tickets > 2 composed into readable boolean rules.

Expression Trees

This tree:

{
    kind: "op",
    op: "gt",
    args: [
        {kind: "var", name: "daysIdle"},
        {kind: "const", value: 7}
    ]
}

means:

daysIdle > 7

discovery.run(program, vars) evaluates the tree. vars is normally one data row.

Escalation Rule Discovery

discovery = import("./src/discover.ns");

rows = [
    {tickets: 0, daysIdle: 1, planValue: 20, outage: 0, escalated: 0},
    {tickets: 3, daysIdle: 8, planValue: 40, outage: 0, escalated: 1},
    {tickets: 4, daysIdle: 4, planValue: 45, outage: 1, escalated: 1}
];

fitness = func(program, tools, ctx) {
    mistakes = 0;
    for (i = 0; i < rows.count(); i = i + 1) {
        score = tools.run(program, rows[i]);
        predicted = score >= 0.5 ? 1 : 0;
        if (predicted != rows[i].escalated) mistakes = mistakes + 1;
    }
    return mistakes + (tools.nodeCount(program) * 0.02);
};

result = discovery.evolve(fitness, {
    searchStrategy: "beam",
    beamWidth: 8,
    maxDepth: 3,
    variables: ["tickets", "daysIdle", "outage"],
    booleanVariables: ["outage"],
    comparisonOperators: ["gt"],
    constants: [0, 1, 2, 3, 5, 7, 10, 50],
    operatorPreset: "rules",
    seed: 31
});

printline(discovery.formatAlgorithm(result));

Rule Beam Search

searchStrategy: "beam" builds atomic rule predicates, keeps the best scoring beam, and composes those predicates with boolean operators. This is usually a better fit for professional rule induction than random expression generation.

FieldPurpose
beamWidthNumber of top candidates retained at each beam depth. Higher values explore more combinations.
booleanVariablesVariables that can be used directly as boolean predicates, for example outage.
comparisonOperatorsComparison operators used to build numeric predicates, for example ["gt"] or ["gt", "lt"].
maxDepthMaximum predicate composition depth. Depth 1 is atomic predicates; depth 3 can express rules such as (a or b) and c.

Beam rule search still uses your fitness function. It is not a hand-coded answer; it enumerates and scores a bounded set of typed candidate rules according to the same objective as evolutionary discovery.

Operator Presets

Operator presets keep the search space manageable. Smaller search spaces run faster and usually produce simpler expressions.

PresetOperatorsUse for
mathadd sub mul div min max abs negNumeric formulas and calibration-like symbolic regression.
comparegt lt eq min maxThreshold comparisons and simple ranking rules.
logicgt lt eq and or not ifBoolean expressions and decision logic.
rulesgt lt eq and or ifReadable decision rules without unary negation.
arithmeticRulesadd sub mul div gt lt eq and or ifRules that need derived numeric expressions.
allAll built-in operatorsOpen-ended searches when runtime is acceptable.

You can override presets with an explicit operator list:

result = discovery.evolve(fitness, {
    variables: ["margin", "risk", "age"],
    constants: [0, 1, 5, 10, 100],
    operators: ["gt", "lt", "and", "or"]
});

Algorithm Discovery Theory

Symbolic discovery is related to genetic programming. Instead of evolving numeric vectors, it evolves programs or expressions. A candidate might be a small rule, a formula, or a conditional expression. The fitness function decides whether that candidate behaves well.

The search is not magic and it does not infer meaning from operator names. Operators are interpreted by evalNode. The generator only chooses from the operators you allow. If you allow gt, the evaluator knows how to run a greater-than comparison. If you allow if, the evaluator knows how to choose between two branches.

Why Limit Operators?

Every extra operator increases the number of possible trees. With four variables, eight constants, and fifteen operators, even shallow trees have a large number of combinations. If your task is a decision rule, starting with rules is usually better than all. If your task is a formula, start with math or arithmeticRules.

Evolution vs Beam Rule Search

Evolutionary discovery is useful when candidate programs can be arbitrary formulas and the useful building blocks are not known in advance. It is stochastic and may need larger populations or more generations.

Beam rule search is deterministic rule induction over typed predicates. It first builds atoms from variables, constants, and comparisonOperators, then composes the best atoms with and / or up to maxDepth. Prefer it for classification, escalation, inspection, policy, and eligibility rules. Restrict variables, booleanVariables, and comparisonOperators to meaningful fields so the beam spends work on plausible rules.

Fitness as Specification

In discovery mode, the fitness function is the specification. For classification, count mistakes. For forecasting, sum error. For a trading rule, combine profit, drawdown, and transaction costs. For operations, combine service level and resource cost. 

fitness = func(program, tools, ctx) {
    loss = 0;
    for (i = 0; i < validationRows.count(); i = i + 1) {
        predicted = tools.run(program, validationRows[i]);
        loss = loss + abs(predicted - validationRows[i].target);
    }
    complexityPenalty = tools.nodeCount(program) * 0.01;
    return loss + complexityPenalty;
};

Complexity Penalty

A discovered expression can overfit the training rows. Penalising node count nudges the search toward smaller, more readable expressions. This is similar to preferring simpler decision trees or regularized statistical models. Remove the penalty when raw fit matters more than readability. Increase it when you want compact rules.

Real-World Example Patterns

Operations Policy Tuning

Tune reorder thresholds, staffing levels, retry delays, or routing weights. Fitness can combine service level, cost, and penalty terms. 

fitness = func(values, ctx) {
    reorderPoint = values[0];
    safetyStock = values[1];
    result = simulateInventory(reorderPoint, safetyStock);
    return result.stockoutDays * 100 + result.holdingCost;
};

Backtest Parameter Search

Tune windows, thresholds, and risk limits. Use penalties so the optimiser does not chase profit while ignoring drawdown. 

fitness = func(values, ctx) {
    shortWindow = values[0];
    longWindow = values[1];
    threshold = values[2];
    stats = backtest(shortWindow, longWindow, threshold);
    return (0 - stats.profit) + (stats.maxDrawdown * 2) + stats.tradeCost;
};

Quality Control Rule Discovery

Discover readable pass/fail rules from inspection rows. Use operatorPreset: "rules" and penalize node count to keep the rule understandable.

Formula Discovery for Sensor Calibration

Use operatorPreset: "math" or "arithmeticRules" when the output is numeric. Score by mean absolute error or squared error against measured outputs.

Tuning and Troubleshooting

SymptomLikely causeWhat to change
Parameter optimisation stallsToo little diversity or bounds too narrowIncrease populationSize, widen bounds, or increase mutationFactor.
Parameter results jump aroundToo much exploration or noisy fitnessLower mutationFactor, increase generations, average noisy scores.
Discovery is slowSearch space too largeUse a narrower operatorPreset, fewer constants, lower maxDepth.
Discovery accuracy is low on rulesEvolution is stuck on simple predicatesUse searchStrategy: "beam", set booleanVariables, and restrict comparisonOperators.
Evolutionary discovery accuracy is lowSearch too small or expression depth too shallowIncrease populationSize, generations, or maxDepth.
Discovered rule is too complexNo complexity pressureAdd tools.nodeCount(program) * penalty to fitness.
Rule overfits training rowsFitness only scores training dataScore validation rows too, or add stronger complexity penalties.
