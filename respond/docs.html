respond Documentation

Turn free-text requests into grounded answers by combining request classification, semantic overlap, lightweight embeddings, and evidence ranking.

Start with examples/demo.ns for the compact example, examples/large_corpus_demo.ns for a broader corpus, or examples/rules_demo.ns for manual rule overrides.

What This Module Does

respond is an orchestration-style tool. You give it a corpus of text and a new request such as a question, prompt, or user message. It trains a small internal system from the corpus, analyzes what the request appears to be asking for, ranks the most relevant evidence segments, and produces a direct answer string.

The important constraint is that the answer stays grounded in the corpus. This module does not call an external model. It synthesizes answers from what it can justify using learned topics, relation patterns, lexical overlap, and embedding similarity.

Use this when you want to step beyond “what is the intent?” and actually produce a user-facing response that is still tied to local evidence.

High-Level Flow

  1. Normalize the input corpus into documents and segment-like rows.
  2. Extract lightweight relation hints such as category, capability, and attribute statements.
  3. Build a semantic co-occurrence map from the corpus.
  4. Create lightweight embeddings for terms and segments.
  5. Analyze the new input to infer likely topics and an intent label.
  6. Rank candidate evidence segments using lexical overlap, topic hits, semantic similarity, and earlier evidence scores.
  7. Synthesize a direct answer string from the best grounded rows.
request -> analyze -> rank evidence -> compose answer

That summary is accurate but compressed. In practice the module does two different jobs:

  • Build a searchable response system from the corpus. This is the training step. It prepares segments, relation rows, co-occurrence structure, topic lookup maps, and term embeddings.
  • Resolve one new request against that system. This is the answer step. It infers likely topics and intent, builds an embedding for the new request, scores all candidate segments, and composes a short grounded answer from the best rows.

The important design point is that the response is not generated from scratch. The module chooses and combines existing grounded corpus rows, and only adds a small amount of response formatting around them.

How The Module Works Internally

1. Corpus Normalization

The module first turns corpusInput into a document list. If you pass one large string with several non-empty lines, each line becomes its own document. If you pass an array of strings, each array entry is already treated as one document.

This matters because later statistics such as co-occurrence, vocabulary frequency, and segmentation all work from this normalized document list.

2. Segment Extraction

Each document is split into smaller evidence rows called segments. A segment is a sentence-like unit cut on:

  • .
  • !
  • ?
  • ;
  • newline

So a corpus line like "billing pages let users download invoices" becomes one segment. A paragraph with multiple sentences becomes several segments.

Segments are the main retrieval units used at answer time. The module does not answer from whole documents. It answers from scored segments, because segments are usually small enough to be precise and large enough to be readable.

3. Relation Hint Extraction

Before doing semantic ranking, the module extracts pair rows and bridge profiles from segment text. These are not deep parses. They are deliberately lightweight structural summaries of segment token order.

Pattern shapeRelation row producedTypical use
X is Y, X are YcategoryRowsDefinition-like answers such as "what is X"
X can ...capabilityRowsCapability checks such as "can X ..."
X has ..., X have ...attributeRowsAttribute-style answers such as "what does X have"
X belong to Y, X belongs to YcategoryRowsTaxonomy or ownership-style definitions

Internally the module first converts a segment into left -> bridge -> right form. Then it groups repeated bridges across the corpus and classifies those bridges statistically into relation families such as category_of, capability_of, attribute_of, explain_topic, or related_to.

These learned relation rows let the module prefer a more direct answer when the bridge evidence suggests a specific relation family. For example, if the request tokens match a bridge profile that the corpus has statistically learned as capability_of, the module can prefer a capability-style row even if a descriptive row scores similarly.

4. Topic and Parent Index Construction

From the extracted relations and retained vocabulary, the module builds:

  • topicIndex: a fast map of candidate topic terms
  • parentIndex: a direct topic-to-parent map from category-style rows

This is what supports output like “poodle” as the direct topic and “dog” as its parent topic.

5. Semantic Co-Occurrence Map

The module walks each document segment with a sliding token window and records which normalized words appear near each other. That produces a local co-occurrence matrix:

{ invoice: {billing: 4, download: 2, overdue: 1}, billing: {invoice: 4, dashboard: 2, page: 1} }

This map is the semantic backbone for the embedding step. The module does not learn embeddings from labels or neural weights. It learns them from local context structure inside the corpus.

6. Embedding Construction

Each retained vocabulary term gets a lightweight embedding built from its co-occurrence neighborhood. Segment embeddings and request embeddings are then built by averaging the embeddings of the terms they contain.

So the module does not embed a whole sentence directly in one step. Instead it:

  1. builds term embeddings from co-occurrence
  2. builds a segment embedding by averaging the segment’s term embeddings
  3. builds a request embedding by averaging the request’s term embeddings

7. Request Analysis

When a new request arrives, the module:

  • tokenizes it
  • normalizes tokens
  • scores likely topics from the topic index and co-occurrence support
  • derives parent topics when a category parent exists
  • assigns a relation family and public intent label from bridge-profile matches and topic-linked corpus relations
  • collects early evidence rows that look topic-relevant

8. Final Candidate Ranking

After analysis, every stored segment is scored again using the final weighted blend. This is the main retrieval pass that produces result.candidates.

9. Manual Rule Layer

If config.intentRules is non-empty, rules run after statistical topic and relation inference.

That ordering matters:

  • the corpus still determines the default topics and relation requests
  • rules do not replace the statistical pipeline
  • rules only override the public intent label, the top inferred relation, or both

This means you can keep the default corpus-driven behavior while adding a few targeted overrides for a domain or application.

9. Answer Composition

The module then chooses how to turn the top-ranked evidence into a response. The strategy depends on intent:

  • define: prefer a category-style row if available
  • capability_check: prefer a capability-style row if available
  • attribute_query: prefer an attribute-style row if available
  • explain: usually combine one or two descriptive rows
  • compare: expose more than one high-ranking row rather than compressing to one statement

The text returned in result.answer is therefore a selection-and-composition step, not free-form generation.

Quick Start

respond = import("./respond.ns").respond; corpus = " poodles are dogs dogs are animals poodles have curly coats dogs can swim "; system = respond.train(corpus, respond.defaultConfig()); result = respond.answer(system, "can dogs swim", 3); printline(result.intent); printline(result.answer);

Typical output meaning:

  • result.intent might be "capability_check".
  • result.answer might be "dogs can swim.".
  • result.candidates contains the ranked evidence rows that led to that answer.

What Segments Are

A segment is the smallest text unit the response system ranks and returns as evidence. You can think of it as the module’s “retrieval chunk”.

{ docIndex: 12, segmentIndex: 0, text: "billing pages let users download invoices", tokens: ["billing", "pages", "let", "users", "download", "invoices"], normalizedTokens: ["billing", "page", "let", "user", "download", "invoice"], embedding: {...} }
FieldMeaning
docIndexWhich normalized document this segment came from.
segmentIndexWhich segment number it was within that document.
textThe original printable segment text.
tokensThe raw lowercase alphanumeric token list.
normalizedTokensThe lighter normalized form used for matching, including simple singularization of some trailing s forms.
embeddingThe segment-level embedding built from the embeddings of the normalized terms it contains.

Why segments matter:

  • Smaller segments make responses more precise.
  • Larger segments give more context but can blur ranking.
  • Since this module uses sentence-like segments, the retrieved evidence usually reads well directly in the final answer.

How Embeddings Are Used

Embeddings in this module are not used to generate text. They are used only to help rank which evidence segments are semantically closest to the new request.

What the embeddings represent

A term embedding is a compact numeric summary of the contexts that term appears in. If two words appear near many of the same neighboring words, their embeddings will tend to be more similar.

For example, if the corpus often places invoice near billing, download, charge, and overdue, then the invoice embedding will carry that context signature.

How the module builds them

  1. Build a co-occurrence map from local token windows.
  2. Hash context terms into a fixed-size vector.
  3. Weight each context contribution by its co-occurrence frequency.
  4. Normalize the resulting vector.

This is a lightweight distributional embedding. It is not a transformer embedding and it is not trained with gradient descent.

Where embeddings affect results

Embeddings affect the embeddingScore part of each candidate row’s final score. That means they help surface semantically related rows even when the wording is not an exact lexical match.

request: "tell me about invoices" candidate A: "invoices belong to billing" candidate B: "billing dashboards show overdue invoices" candidate C: "account pages show payment history" embedding similarity helps A and B stay high because they live in the same invoice/billing context neighborhood, even if the exact token overlap differs.

What embeddings do not do

  • They do not choose the intent label directly.
  • They do not replace lexical matching.
  • They do not override direct relation rows when the module already has a stronger exact answer form.
  • They do not generate paraphrases.

Practical effect

If you reduce embedding influence, the module becomes more literal and keyword-driven. If you increase embedding influence, the module becomes more tolerant of wording variation but may sometimes rank semantically related rows above the most explicit one.

Config In Depth

The config controls three broad behaviors:

  • how rich the semantic representation is
  • how much evidence is retained and exposed
  • how the final ranking balances exact matches versus semantic matches

dimensions

What it is: embedding vector width for terms, requests, and segments.

Lower values: faster and simpler, but more collisions between unrelated context terms. Semantic ranking becomes cruder.

Higher values: more room to distinguish different context neighborhoods, which can improve semantic separation in larger corpora. Past a point, gains flatten and runtime/storage rise.

Typical effect on results: if your corpus spans many domains, increasing this can help keep those domains apart. If your corpus is tiny and simple, changing it may have little visible effect.

semanticWindow

What it is: how far left and right the co-occurrence pass looks when deciding which words are neighbors.

Smaller values: tighter, more local meanings. Better when you want context to stay precise.

Larger values: broader context neighborhoods. Better when important terms are often separated by a few words, but too large a window can blur unrelated words together.

Typical effect on results: increasing this can make semantic retrieval more forgiving, but also more diffuse.

vocabLimit

What it is: maximum number of frequent vocabulary terms that get prebuilt reusable embeddings.

Lower values: smaller, faster system, but more rare terms fall back to on-the-fly embedding construction or weaker frequency-only behavior.

Higher values: better coverage of the corpus vocabulary, especially in larger or more varied corpora, at the cost of more preprocessing and memory.

Typical effect on results: raising this helps when useful topic words are moderately frequent but not in the top core vocabulary.

segmentLimit

What it is: default maximum number of candidate evidence rows returned by answer(...) when you do not pass an explicit limit.

Lower values: less output, simpler debugging, fewer returned candidates.

Higher values: more candidate visibility for inspection or UI rendering, but also more noise if you surface all of them directly to users.

Typical effect on results: it does not change how the best row is scored. It changes how many ranked rows you keep and expose.

topicLimit

What it is: default maximum number of direct topic rows exposed by analyze(...).

Lower values: a narrower view of what the system thinks the request is about.

Higher values: more visibility into secondary topic guesses, which can be useful for debugging but may include weaker or noisier topic rows.

answerEvidenceLimit

What it is: a reserved answer-composition budget field.

Current implementation status: the module already tends to compose from the top one or two rows, so this field is more of a policy signal than a hard runtime constraint right now.

How to think about it: it expresses how much raw evidence you conceptually want to expose in one answer before the response becomes too long or mixed.

scoreWeights.evidence

What it is: how much to trust the earlier topic-focused evidence score in final ranking.

Increase it: final candidates stay closer to topic-first analysis.

Decrease it: final ranking relies more on lexical and embedding similarity.

Typical effect on results: higher values make the system more conservative around the detected topic.

scoreWeights.embedding

What it is: how much semantic similarity matters in final ranking.

Increase it: semantically related rows can beat literal keyword rows more often.

Decrease it: the system becomes more literal and exact-match oriented.

Typical effect on results: useful when users phrase requests differently from the corpus wording.

scoreWeights.lexical

What it is: how much direct token overlap matters.

Increase it: exact wording matches rise in the ranking.

Decrease it: semantic and topic-based matches matter relatively more.

Typical effect on results: good to raise when your corpus uses very explicit, repetitive terminology and exact wording should dominate.

scoreWeights.topic

What it is: how much direct topic and parent-topic hits matter.

Increase it: rows that explicitly mention the chosen topic get boosted harder.

Decrease it: more indirect but semantically related rows have a better chance to surface.

Typical effect on results: useful when you want responses to stay tightly anchored to the detected entity or concept.

intentLabels

What it is: the public names exposed for internal relation families.

Changing these does not change the underlying ranking behavior. It changes the labels you see in analysis.intent and result.intent.

For example, you could rename capability_check to ability_query without changing how capability requests are detected or answered.

intentRules

What it is: an optional manual rule layer that runs after statistical relation inference and can override the top public intent or relation.

Why it exists: the module stays corpus-driven by default, but you may still want a controlled override for a domain, interface, or product vocabulary.

What it can override:

  • label: override the final public analysis.intent
  • relation: override the top relation request before intent-label mapping

Supported rule fields:

FieldMeaning
labelOptional explicit public intent label, such as question or help.
relationOptional internal relation override, such as attribute_of or capability_of.
priorityHigher-priority rules win when more than one rule matches.
containsAnyAt least one of these tokens must appear.
containsAllAll listed tokens must appear.
containsNoneNone of the listed tokens may appear.
sequenceOrdered token-pattern match supporting word, oneOf, topic, parentTopic, wildcard, and optional.
relationAnyRequire at least one inferred relation request to match one of the listed relation kinds.
relationAllRequire all listed relation kinds to be present in the inferred relation requests.

How matching works:

  • containsAny, containsAll, and containsNone are simple lexical gates over normalized request tokens.
  • sequence is an ordered pattern matcher. It can skip filler tokens between the listed items.
  • topic and parentTopic refer to the statistically detected topics for the current request.
  • relationAny and relationAll refer to the statistically inferred relation requests, not raw lexical cues.
  • If multiple rules match, the rule with the highest priority wins.

Supported sequence items:

Pattern itemMeaningExample
"what"String shorthand for an exact word match.Matches the normalized token what.
{kind: "word", value: "reset"}Exact word match written explicitly.Useful when building longer structured sequences.
{kind: "oneOf", words: ["help", "support"]}Matches any one token from the list.Useful for domain-specific cue sets.
{kind: "topic"}Matches a detected direct topic token.Lets a rule refer to “whatever topic was inferred here”.
{kind: "parentTopic"}Matches a detected parent-topic token.Useful when a rule should fire only for broader classes.
{kind: "wildcard"}Matches zero or more tokens.Useful when you do not know how many filler words may appear between two important items.
{kind: "optional", item: ...}Matches zero or one occurrence of the inner item.Useful when one token may or may not be present.
{kind: "any"}Matches any single token.Use when position matters but content does not.
config.intentRules = [{ label: "question", priority: 100, containsAny: ["what"], sequence: [ {kind: "word", value: "what"}, {kind: "topic"} ] }];

That example overrides the final public intent to question whenever the normalized request tokens contain what followed later by a detected topic.

config.intentRules = [{ relation: "attribute_of", priority: 80, containsAny: ["what"], sequence: [ {kind: "word", value: "what"}, {kind: "topic"} ] }];

That example does not set a custom public label directly. Instead it overrides the top inferred relation to attribute_of. The final public intent then becomes whatever intentLabels.attribute_of is currently mapped to, which defaults to attribute_query.

config.intentRules = [{ label: "help", priority: 120, containsAny: ["reset", "recovery"], relationAny: ["explain_topic", "related_to"], sequence: [ {kind: "word", value: "reset"}, {kind: "wildcard"}, {kind: "topic"} ] }];

That example shows a more cautious override: it only fires if the lexical cues match and the statistical relation inference already looks like descriptive or generic topic evidence.

See examples/rules_demo.ns for a runnable demonstration of all three patterns above.

How Candidate Scoring Works

Each segment gets a final score from four ingredients:

  • Evidence score: whether the segment was already a good match during topic-focused analysis.
  • Embedding score: cosine similarity between the request embedding and the segment embedding.
  • Lexical score: direct token overlap between the request and the segment.
  • Topic score: whether the segment contains the detected topic or parent-topic words.
finalScore = evidenceWeight * evidenceScore + embeddingWeight * embeddingScore + lexicalWeight * lexicalScore + topicWeight * topicScore

This means a segment can rank well either because it is a direct lexical match, because it is semantically close, or because it is strongly tied to the inferred topic.

Score fieldWhat it measuresWhy it matters
evidenceScoreHow strong the segment already looked during early topic-focused evidence selection.Preserves the first-pass topic grounding.
embeddingScoreSemantic similarity between request embedding and segment embedding.Helps with wording variation and related concepts.
lexicalScoreDirect normalized token overlap between the request and the segment.Rewards exact or near-exact wording matches.
topicScoreWhether the segment explicitly mentions the inferred topic or parent topic.Keeps retrieval anchored to the detected subject.

Current Limits

  • Relation extraction is intentionally lightweight. It uses endpoint-plus-bridge structure and repeated bridge statistics rather than deep parsing.
  • Token normalization is lightweight and mainly lowercases plus singularizes some trailing s forms.
  • There is no external world knowledge. If the corpus does not support an answer, the module can only return grounded fallback evidence.
  • The scoring and relation inference are lightweight statistical heuristics. They are designed for transparent behavior and local control, not full conversational generality.
  • Rules are overrides, not full parsers. They are best used to steer or relabel the existing statistical behavior, not to encode an entire language-specific grammar.
