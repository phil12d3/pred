respond Documentation

Turn free-text requests into grounded answers by combining request classification, semantic overlap, lightweight embeddings, and evidence ranking.

Start with examples/demo.ns if you want a working example first.

What This Module Does

respond is an orchestration-style tool. You give it a corpus of text and a new request such as a question, prompt, or user message. It trains a small internal system from the corpus, analyzes what the request appears to be asking for, ranks the most relevant evidence segments, and produces a direct answer string.

The important constraint is that the answer stays grounded in the corpus. This module does not call an external model. It synthesizes answers from what it can justify using learned topics, relation patterns, lexical overlap, and embedding similarity.

Use this when you want to step beyond “what is the intent?” and actually produce a user-facing response that is still tied to local evidence.

High-Level Flow

  1. Normalize the input corpus into documents and segment-like rows.
  2. Extract lightweight relation hints such as category, capability, and attribute statements.
  3. Build a semantic co-occurrence map from the corpus.
  4. Create lightweight embeddings for terms and segments.
  5. Analyze the new input to infer likely topics and an intent label.
  6. Rank candidate evidence segments using lexical overlap, topic hits, semantic similarity, and earlier evidence scores.
  7. Synthesize a direct answer string from the best grounded rows.
request -> analyze -> rank evidence -> compose answer

Quick Start

respond = import("./respond.ns").respond; corpus = " poodles are dogs dogs are animals poodles have curly coats dogs can swim "; system = respond.train(corpus, respond.defaultConfig()); result = respond.answer(system, "can dogs swim", 3); printline(result.intent); printline(result.answer);

Typical output meaning:

  • result.intent might be "capability_check".
  • result.answer might be "dogs can swim.".
  • result.candidates contains the ranked evidence rows that led to that answer.

Public API

defaultConfig()

Use it for: getting a safe baseline config object.
Returns: an object with embedding, ranking, and intent-label defaults.

This function takes no parameters. Call it when you want the module’s standard behavior before overriding a few fields.

train(corpusInput, config)

Use it for: building a reusable response system from one text source or a list of text sources.
Returns: a trained system object containing normalized docs, co-occurrence data, embeddings, relation rows, topic index, and segment rows.
ParameterTypeWhat it means
corpusInputstring or array of stringsThe source knowledge the module is allowed to answer from. A single string may be one document or a multi-line block. An array lets you pass separate source texts explicitly.
configobject, optionalControls embedding size, ranking weights, vocabulary cap, and how many topics or evidence segments are exposed by default. If omitted, defaultConfig() is used.

train(...) does not answer anything by itself. It creates a reusable system object so you can run many requests against the same corpus without rebuilding everything each time.

analyze(system, inputText, limit)

Use it for: inspecting what the module thinks the request is asking for before you generate a final answer.
Returns: topics, parent topics, the requested relation family, the final intent label, and supporting evidence rows.
ParameterTypeWhat it means
systemtrained system objectThe object returned by train(...). It contains the learned documents, segments, semantic map, relation rows, and embeddings used during analysis.
inputTextstringThe new request to interpret, such as "what is a poodle" or "tell me about invoices".
limitnumber, optionalThe maximum number of direct topic rows exposed in analysis.topics. It is not a token limit, not a document limit, and not the number of final answer sentences. If omitted, system.config.topicLimit is used.

Important detail: analyze(...) always computes evidence rows internally, but its limit parameter only caps the number of direct topics returned in the public topics array.

answer(system, inputText, limit)

Use it for: the main end-to-end request handling path.
Returns: a full result object with the analysis, ranked candidates, query tokens, and a direct answer string.
ParameterTypeWhat it means
systemtrained system objectThe object returned by train(...).
inputTextstringThe new request to answer.
limitnumber, optionalThe maximum number of final ranked evidence rows returned in result.candidates. It does not limit training, tokenization, or topic detection. If omitted, system.config.segmentLimit is used.

This is the most important difference from analyze(...):

  • In analyze(...), limit means the maximum number of topic rows returned.
  • In answer(...), limit means the maximum number of ranked evidence candidates returned.

The answer text itself is usually built from the top one or two candidates, even if you request a larger candidate limit.

reply(system, inputText, limit)

Use it for: a naming alias when “reply” reads better than “answer”.
Current behavior: this is an alias for answer().
ParameterTypeWhat it means
systemtrained system objectSame as answer(...).
inputTextstringSame as answer(...).
limitnumber, optionalSame as answer(...): the maximum number of ranked candidate rows in result.candidates.

render(result)

Use it for: turning a result object into compact human-readable lines for terminal output or debugging.
Returns: an array of strings.
ParameterTypeWhat it means
resultanswer result objectThe object returned by answer(...) or reply(...). render(...) expects fields such as input, intent, answer, and candidates.

render(...) does not re-rank or re-analyze anything. It only formats an existing result into readable lines.

config for train(...)

If you omit config, the module uses respond.defaultConfig().

FieldDefaultMeaning
dimensions12Embedding vector width used for terms, queries, and segments. Larger values give more room for the hashed co-occurrence signal.
semanticWindow2How many tokens to the left and right count as co-occurrence context when building the semantic map.
vocabLimit128Maximum number of frequent vocabulary items to keep when building reusable term embeddings.
segmentLimit5How many evidence segments to keep in analysis and final candidate ranking by default.
topicLimit3How many direct topics to expose from analysis.
answerEvidenceLimit2Reserved answer-synthesis budget. In the current implementation the answer usually uses at most the top one or two pieces of evidence.
scoreWeights.evidence0.45Weight for earlier topic-evidence score during final candidate ranking.
scoreWeights.embedding0.30Weight for embedding similarity between the request and a segment.
scoreWeights.lexical0.15Weight for token overlap between the request and a segment.
scoreWeights.topic0.10Weight for direct topic and parent-topic hits inside a segment.
intentLabelsmapping objectPublic labels exposed for relation families. Current defaults include define, capability_check, attribute_query, compare, relation_query, and explain.

inputText for analyze(...), answer(...), reply(...)

This is the new user request. It may be a question, command-like request, or short free-text prompt such as:

  • "what is a poodle"
  • "can dogs swim"
  • "tell me about invoices"

limit for analyze(...), answer(...), reply(...)

limit does not mean one universal thing across the whole API. It depends on which function you call:

  • For analyze(...), limit is the maximum number of direct topic rows returned in analysis.topics.
  • For answer(...) and reply(...), limit is the maximum number of final ranked candidate rows returned in result.candidates.

So if you call answer(system, "can dogs swim", 3), the 3 means “return at most 3 ranked evidence candidates”. It does not mean “return 3 tokens”, “use only 3 documents”, or “generate 3 answer sentences”.

Trained System Object

train(...) returns an internal system object. You usually pass it straight into analyze() or answer(), but it is useful to know what it contains.

{ config: {...}, docs: [...], cooc: {...}, vocab: [...], termEmbeddings: {...}, relations: { categoryRows: [...], capabilityRows: [...], attributeRows: [...] }, topicIndex: {...}, parentIndex: {...}, segments: [...] }
FieldMeaning
docsThe normalized document list built from the original corpus input.
coocThe semantic co-occurrence matrix used for embedding construction and similarity support.
vocabThe retained vocabulary used for reusable term embeddings.
termEmbeddingsA map of term to embedding object.
relations.categoryRowsSimple category-like rows such as poodles are dogs.
relations.capabilityRowsCapability-like rows such as dogs can swim.
relations.attributeRowsAttribute-like rows such as poodles have curly coats.
topicIndexA fast topic lookup map built from relation rows and vocabulary.
parentIndexDirect topic-to-parent mapping learned from category-style rows.
segmentsThe segmented evidence rows, each with text, tokens, normalized tokens, and an embedding.

Analysis Output

analyze(system, inputText, limit) returns an interpretation of the request before final answer synthesis.

{ input: "can dogs swim", topics: [{word: "dog", score: 1.2}], parentTopics: [{word: "animal", fromTopic: "dog", score: 0.96}], relationsRequested: [{relation: "capability_of", score: 1}], rulesMatched: [], matchedRule: null, intent: "capability_check", intentSource: "relation", evidence: { inputKeywords: ["can", "dog", "swim"], matchingSegments: [...], parentSegments: [] } }
FieldMeaningWhat to use it for
topicsThe direct things the system thinks the request is about.Inspecting the main subject of the request.
parentTopicsBroader classes inherited from category-style rows.Fallback reasoning or broader context.
relationsRequestedThe relation family the request most resembles.Intent-specific routing or debugging.
intentThe public label exposed for that relation.Branching to different answer or tool behavior.
evidence.matchingSegmentsSegments already scored as topic-relevant before final ranking.Early evidence inspection.
evidence.inputKeywordsNormalized request keywords.Debugging tokenization and normalization.

Answer Output

answer(system, inputText, limit) wraps analysis plus final ranking and answer synthesis.

{ input: "what is a poodle", intent: "define", analysis: {...}, queryTokens: ["what", "is", "a", "poodle"], candidates: [ { text: "poodles are dogs", score: 0.66, lexicalScore: 0.25, embeddingScore: 0.72, evidenceScore: 0.80, topicScore: 1, docIndex: 0, segmentIndex: 0, rank: 1 } ], answer: "poodles are dogs." }
FieldMeaning
analysisThe full analysis object described above.
queryTokensThe raw request tokens before singular-style normalization.
candidatesThe final ranked evidence rows after lexical, embedding, topic, and evidence-score blending.
answerThe direct user-facing response synthesized from the strongest grounded evidence.

How Candidate Scoring Works

Each segment gets a final score from four ingredients:

  • Evidence score: whether the segment was already a good match during topic-focused analysis.
  • Embedding score: cosine similarity between the request embedding and the segment embedding.
  • Lexical score: direct token overlap between the request and the segment.
  • Topic score: whether the segment contains the detected topic or parent-topic words.
finalScore = evidenceWeight * evidenceScore + embeddingWeight * embeddingScore + lexicalWeight * lexicalScore + topicWeight * topicScore

This means a segment can rank well either because it is a direct lexical match, because it is semantically close, or because it is strongly tied to the inferred topic.

Intent Labels in Current Behavior

IntentTypical trigger shapeTypical answer strategy
definewhat is X, who is XPrefer category-style evidence such as X is Y.
capability_checkcan X ..., could X ...Prefer capability-style evidence such as X can ....
attribute_queryRequests involving has or havePrefer attribute-style evidence such as X has ....
compareExplicit compare cues or multiple strong topicsReturn the closest comparison evidence rows rather than one compressed definition.
relation_queryFallback relation-style requestReturn the strongest general evidence.
explaintell me about X or topic-only promptsReturn one or two descriptive evidence rows.
The current implementation uses simple heuristic intent detection. It is intentionally lightweight and grounded in the local corpus rather than a full language model.

Examples

Definition Example

corpus = " poodles are dogs dogs are animals poodles have curly coats "; system = respond.train(corpus, respond.defaultConfig()); result = respond.answer(system, "what is a poodle", 3); printline(result.intent); // define printline(result.answer); // poodles are dogs.

Capability Example

corpus = " dogs are animals dogs can swim birds can fly "; system = respond.train(corpus, respond.defaultConfig()); result = respond.answer(system, "can dogs swim", 3); printline(result.intent); // capability_check printline(result.answer); // dogs can swim.

Explain Example

corpus = " invoices belong to billing billing pages let users download invoices account pages show payment history "; system = respond.train(corpus, respond.defaultConfig()); result = respond.answer(system, "tell me about invoices", 3); printline(result.intent); // explain printline(result.answer); // invoice: invoices belong to billing. billing pages let users download invoices.

Debugging with analyze(...)

analysis = respond.analyze(system, "can dogs swim", 3); printraw(analysis.topics); printraw(analysis.relationsRequested); printraw(analysis.evidence.matchingSegments);

Use this path when you want to inspect why the module chose a particular answer before showing it to the user.

render(result)

render(...) returns printable lines in this shape:

Input: can dogs swim Intent: capability_check Answer: dogs can swim. Top evidence: 1. score=1 text=dogs can swim 2. score=0.71 text=dogs are animals

This is meant for terminal display, logs, demos, or quick inspection during development.

Current Limits

  • Relation extraction is intentionally simple and currently favors patterns like X is Y, X can ..., X has ..., and X belongs to Y.
  • Token normalization is lightweight and mainly lowercases plus singularizes some trailing s forms.
  • There is no external world knowledge. If the corpus does not support an answer, the module can only return grounded fallback evidence.
  • The scoring and intent logic are heuristic. They are designed for transparent behavior and local control, not full conversational generality.
