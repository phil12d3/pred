intent Documentation

Topic-first, relation-aware intent analysis from raw corpus text.

The module now focuses on what your example actually needs: learn a corpus model, find the main topic terms in new input, infer what relation family is being requested, and map that to a stable intent label.

Target Behavior

"What is a poodle?" topics: ["poodle"] parentTopics: ["dogs", "animals"] relationsRequested: ["category_of"] intent: "define" "Can dogs swim?" topics: ["dogs", "swim"] parentTopics: ["animals"] relationsRequested: ["capability_of"] intent: "capability_check"

This is the contract the module is now built around.

Output Fields

intent.analyze(...) returns several layers of output. They are related, but they are not the same thing.

FieldWhat it meansWhat it is not
topicsThe main terms from the input that the model believes the user is directly asking about.Not the broader class. Not the final intent label.
parentTopicsBroader classes inherited from learned category_of links. These provide context above the direct topic.Not replacements for the main topic. Not proof of the requested relation by themselves.
relationsRequestedThe learned relation family that the input appears to be asking for, such as category_of or capability_of.Not the same as the topic. Not the same as the user-facing intent label.
rulesMatchedDeclarative rules that matched the input. These can override the relation-based intent.Not the raw corpus evidence. These are rule hits, not learned bridge profiles.
matchedRuleThe highest-ranked matched rule, if any.Not the corpus-derived relation request.
intentSourceTells you whether the final intent came from a rule or from the relation mapping fallback.Not the intent label itself.
intentThe normalized public label produced from the strongest relation, such as define or capability_check.Not directly learned as a word from the corpus. It is a configured label.
evidence.matchingSegmentsDirect corpus segments that support the main topic match.Not inherited parent evidence.
evidence.parentSegmentsCorpus segments that explain why a parent topic was inherited.Not the primary evidence for the direct topic match.

Topics Vs Parents Vs Relations

The easiest way to read the output is:

  • topics answers: "what thing in the input is the user talking about?"
  • parentTopics answers: "what broader class does that thing belong to?"
  • relationsRequested answers: "what kind of information is being asked about that thing?"
  • intent answers: "what public label do we want to expose for that relation?"
Input: "what is a poodle" topics: - poodle parentTopics: - dogs - animals relationsRequested: - category_of intent: - define

In that example:

  • poodle is the direct topic because it is what the input is about.
  • dogs and animals are parent topics because they are broader classes reached through learned category links.
  • category_of is the requested relation because the input is asking for the class or kind of the topic.
  • define is just the public label mapped from category_of.
Input: "can dogs swim" topics: - dogs - swim parentTopics: - animals relationsRequested: - capability_of intent: - capability_check

Here the difference matters:

  • dogs is still the thing being asked about.
  • animals is only inherited context.
  • capability_of is the relation because the input is asking whether the topic can do something.
  • capability_check is the public intent label for that relation.

Rule Layer

Rules sit on top of the corpus learner. The corpus still learns topics, parents, bridge families, and relation requests. Rules only decide how to label an input when a shape matches.

This is the order of operations:

  1. Train the corpus model.
  2. Analyze the new input into topics, parent topics, and relation requests.
  3. Try the declarative rules in config.intentRules.
  4. If a rule matches, its label becomes the intent.
  5. If no rule matches, fall back to the relation-to-intent mapping.

Rule Object Fields

FieldTypeMeaning
labelstringRequired. The intent label to return if the rule matches, such as question or help.
prioritynumberOptional. Higher values win when more than one rule matches. Default is 0.

containsAllstring or arrayOptional. Every listed word must appear in the input.
containsNonestring or arrayOptional. None of these words may appear in the input.
sequencearrayOptional. An ordered pattern the input must satisfy. The matcher can skip words between items.
relationAnystring or arrayOptional. At least one learned relation request must match one of these relation kinds.
relationAllstring or arrayOptional. Every listed relation kind must be present in the analyzed input.
topicCountMinnumberOptional. Minimum number of direct topics required.
topicCountMaxnumberOptional. Maximum number of direct topics allowed.
parentTopicCountMinnumberOptional. Minimum number of inherited parent topics required.

Pattern Item Types

The sequence array is made from pattern items. A string item means an exact word match. Objects let you describe richer shapes.

Pattern itemMeaningExample
"what"Exact word match shorthand.The input must contain the word what.
{ kind: "word", value: "what" }Exact word match written explicitly.Same as the string shorthand.
{ kind: "oneOf", words: ["what", "how", "why"] }Matches any one word from the list.Useful for cue-word groups.
{ kind: "topic" }Matches any analyzed topic token.Lets the rule refer to the thing being asked about.
{ kind: "parentTopic" }Matches any inherited parent topic token.Useful when a rule should fire on broader inherited classes.
{ kind: "any" }Matches any token.Useful as a free spacer position.
{ kind: "wildcard" }Matches zero or more tokens.Useful when you do not know how many filler words are in between.
{ kind: "optional", item: ... }Matches either zero or one occurrence of the inner item.Useful when a word may or may not be present.

How Matching Works

  • containsAny and containsAll look for literal words in the input tokens.
  • sequence items must appear in order, but the matcher can skip words between them.
  • wildcard can absorb any number of words.
  • optional can be omitted entirely or matched once.
  • Rules are ranked by priority first, then by how much structure they match.
intentRules = [ { label: "question", priority: 100, containsAny: ["what", "how", "why"], sequence: [ { kind: "oneOf", words: ["what", "how", "why"] }, { kind: "topic" } ] } ]

That rule means: if the input contains one of the cue words and then later contains a topic, label it question. It can match what is a poodle because the matcher is allowed to skip filler words between the cue word and the topic.

containsAny and { kind: "oneOf", ... } may look redundant, but they operate at different levels. containsAny is a top-level lexical gate: at least one listed word must appear somewhere in the input. The oneOf item is part of the ordered sequence: one of those words must appear at that point in the rule shape. If your sequence already spells out the same cue words, containsAny is often optional. It becomes more useful when the sequence only describes structure such as topic, parentTopic, or wildcard and you still want a separate cue-word requirement.

intentRules = [ { label: "help", priority: 50, containsAny: ["help", "support"], containsNone: ["error"], sequence: [ { kind: "oneOf", words: ["help", "support"] }, { kind: "wildcard" }, { kind: "topic" } ] } ]

If a rule matches, intent comes from the rule label and intentSource becomes rule. If no rule matches, the module falls back to the relation-to-intent mapping.

Pipeline

  1. Normalize the input corpus into documents.
  2. Split documents into sentence-like segments.
  3. Split each corpus segment into a simple left / bridge / right pattern.
  4. Learn bridge families from repeated segment patterns across the corpus.
  5. Build a topic vocabulary from words that appear on the left or right side of those pairs.
  6. When new text arrives, match input tokens to learned topic words.
  7. Walk learned category_of links upward to collect broader parent topics.
  8. Use the remaining cue tokens and the learned bridge families to infer which relation is being requested.
  9. Map that learned relation kind to a stable intent label.

What It Learns

The module learns from corpus segments directly:

  • topics: words that repeatedly appear as the left or right side of corpus pairs
  • parent topics: broader classes reached by walking learned category_of links
  • bridge families: repeated middle patterns such as are or can
  • relation kinds: learned families normalized to labels like category_of and capability_of
  • evidence segments: corpus segments most relevant to the new input
The topic and relation learning are corpus-driven. The final normalized intent labels such as define and capability_check come from config.intentLabels. In other words, the corpus learns the relation family, and the config names that family.

Label Glossary

The module uses two separate label layers. One layer names learned relation kinds. The other layer exposes public intent labels for callers.

Relation Kinds

LabelMeaning in the module
category_ofThe corpus suggests that the topic belongs to a broader class. This is the relation used for definition-style queries and parent-topic inheritance.
capability_ofThe corpus suggests an action or capability associated with the topic. This usually means the bridge repeats across multiple different subjects.
attribute_ofThe corpus suggests a descriptive property, feature, or quality of the topic.
compare_topicsThe input is treating two topics as the main items to compare.
related_toThe input points to a related concept, but not a stronger category, capability, or attribute relation.
explain_topicA learned descriptive relation for repeated corpus rows that describe one topic through the same bridge pattern, rather than place it in a broader class. This usually means the same subject keeps repeating while the right side varies with descriptive details.

Public Intent Labels

LabelMeaning for the caller
defineCategory lookup. The input is asking what class or kind the topic belongs to.
capability_checkCapability lookup. The input is asking whether the topic can do something.
attribute_queryAttribute lookup. The input is asking about a property or feature of the topic.
compareComparison request. The input is centered on two topics and their differences or similarities.
relation_queryGeneral relation lookup. The input is asking for a connection that is not stronger than the other labels.
explainExplanation-style request. The input is asking for more context or detail about the topic.
exploreFallback when the module cannot confidently map the input to a stronger relation.

Stage 1: Pair Learning

Each training segment is reduced to a simple pattern:

poodles are dogs left = poodles bridge = are right = dogs dogs can swim left = dogs bridge = can right = swim

Those rows are then grouped by bridge text so the system can learn repeated relation families from the corpus itself.

Stage 2: Topic Detection

At training time, the module builds a topic vocabulary from words that appear on the left or right side of learned pairs. At analysis time, each input token is scored against those topic words using:

  • exact token overlap
  • keyword overlap
  • fuzzy word similarity
  • pair support in the corpus
input: "what is a poodle" candidate topic scores: poodle -> strong exact match dogs -> weaker related term animals -> weaker related term

The highest-scoring terms become analysis.topics.

Stage 3: Parent Topic Inference

After direct topics are selected, the module walks upward through learned category_of links and returns broader classes separately in analysis.parentTopics.

poodles are dogs dogs are animals input topic: poodle parent topics: - dogs - animals

This keeps the queried topic as the main result while still exposing useful inherited context.

Stage 4: Relation Request Detection

For each input, the module then looks at the non-topic cue tokens and checks which learned bridge family they match.

Learned relationTypical meaningHow the corpus shape differs
category_ofA bridge family whose right-hand terms often reappear as left-hand terms elsewhere in the corpus.Right side looks reusable as a broader class.
capability_ofA repeated bridge family that links many left-hand topics to action-like right-hand terms.The same bridge appears across multiple subjects.
explain_topicA repeated descriptive bridge family for one topic.The same left side repeats while the right side varies with details.
attribute_ofA bridge family that tends to attach descriptive right-hand terms to a topic.Usually a single descriptive row or a lighter pattern than explain.
compare_topicsThe input strongly mentions two topics.Two topics are both primary.
related_toThe input refers to peer or neighboring concepts.No stronger family won.
corpus rows: dogs can swim birds can fly learned bridge family: bridge = can kind = capability_of input: "can dogs swim" topic: dogs cue token match: can relation requested: capability_of
corpus rows: poodles are known for curly coats poodles are known for intelligence poodles are known for elegance learned bridge family: bridge = are known for kind = explain_topic input: "poodles" topic: poodles relation requested: explain_topic

Stage 5: Intent Mapping

The module then maps the strongest learned relation to a stable intent label. In practice, explain_topic is produced when the corpus contains repeated descriptive rows for one topic and no stronger category/capability/attribute relation wins. This mapping only runs when no declarative rule matched first.

RelationIntent

capability_ofcapability_check
attribute_ofattribute_query

This is the fallback label mapping. The public intent labels are configured in intent.defaultConfig().intentLabels, so you can rename them if your application wants different vocabulary.

Evidence

The module returns both direct and inherited evidence.

analysis.evidence.matchingSegments = [ { text: "poodles are dogs", score: ... }, { text: "poodles have curly coats", score: ... } ] analysis.evidence.parentSegments = [ { topic: "dogs", fromTopic: "poodle", text: "poodles are dogs", ... }, { topic: "animals", fromTopic: "poodle", text: "dogs are animals", ... } ]

The direct rows explain the primary match. The parent rows explain inherited broader classes.

Evidence fieldPurpose
matchingSegmentsShow the best segments for the input itself and the direct topic match.
parentSegmentsShow which corpus statements caused a parent topic to be inherited.

API

FunctionPurpose
intent.defaultConfig()Return default limits and thresholds.
intent.train(corpusInput, config)Build the corpus model.
intent.analyze(system, inputText, limit)Return topics, parent topics, relations requested, intent, and evidence.
intent.responses(system, inputText, limit)Return evidence segments in a flatter response-oriented shape.

Example

intent = import("./intent.ns").intent; corpus = " poodles are dogs dogs are animals cats are animals poodles have curly coats dogs can swim "; system = intent.train(corpus, intent.defaultConfig()); defineQuery = intent.analyze(system, "what is a poodle", 3); capabilityQuery = intent.analyze(system, "can dogs swim", 3);

Expected style of output:

  • what is a poodle -> topic poodle, parent topics dogs then animals, relation category_of, intent define
  • can dogs swim -> topics dogs, swim, parent topic animals, relation capability_of, intent capability_check

Current Gaps

  • Stable intent labels still require a small explicit mapping layer.
  • Definition detection works best when the corpus contains category statements like X are Y.
  • Capability detection works best when the corpus contains behavior statements like dogs can swim.
  • The module is topic-first; it is not a general conversational intent engine yet.
