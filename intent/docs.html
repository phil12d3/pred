intent Documentation

Corpus-driven intent and utterance-type discovery.

The module trains from raw text, not labeled question/answer rows. It turns a corpus into chunk-level semantic profiles, then uses those profiles to infer topic, utterance form, and response candidates for new input.

Overview

The pipeline has five main stages:

  1. Normalize the corpus input into documents.
  2. Chunk each document into overlapping windows of tokens.
  3. Build semantic topic profiles from keywords, clusters, and word families.
  4. Build utterance-type profiles from repeated structural patterns.
  5. Score new input against both profile sets and return nearby corpus context as responses.
Nothing in this stage requires hardcoded English question words like what or how. The learner depends on repeated patterns and semantic evidence inside the corpus itself.

Input

Input formHow it is handled
"large text..."Trained as one corpus source. If it contains several non-empty lines, each line becomes a separate corpus unit first.
["doc one", "doc two"]Each string is treated as its own document.
multi-line stringPreferred when you already have one utterance or one response block per line.
corpus = " como resetear clave usar enlace reset ahora como cambiar correo abrir ajustes perfil ahora donde ver facturas abrir pagina cobros ahora donde descargar recibos abrir pagina cobros ahora error clave bloqueada soporte revisa caso ahora ";

In that example, the trainer sees five separate corpus units because there are five non-empty lines.

Stage 1: Normalization

intent.train(...) first converts the input to a list of plain text documents.

  • If the caller passes a list, each element is stringified and kept as one document.
  • If the caller passes one string with several non-empty lines, each line becomes a document.
  • If the caller passes one string with no useful line breaks, it stays as one document and later chunking handles the segmentation.
// Input "a line about passwords a line about invoices" // After normalization [ "a line about passwords", "a line about invoices" ]

This step matters because later response extraction uses local neighborhood inside each document. If the corpus already has natural line boundaries, preserving them gives cleaner context windows.

Stage 2: Chunking

Each normalized document is tokenized and then split into chunks. The config controls this with chunkSize and chunkStride.

// Example tokens ["how", "do", "reset", "password", "use", "reset", "link", "now"] // chunkSize = 4, chunkStride = 2 chunk 0 = ["how", "do", "reset", "password"] chunk 1 = ["reset", "password", "use", "reset"] chunk 2 = ["use", "reset", "link", "now"]

Each chunk becomes a training row with these kinds of fields:

FieldMeaning
textThe chunk joined back into text.
tokensThe token array for the chunk.
lead1, lead2The first one or two tokens. These capture repeated openers.
tail1, tail2The last one or two tokens. These capture repeated endings.
lengthA coarse size bucket: short, medium, or long.

Stage 3: Topic / Intent Learning

The module learns topic labels from chunk content in three layers.

3a. Keywords

Each chunk gets TF-IDF-like keyword rows from text-stat. These highlight chunk-specific content words.

chunk text: "download invoice pdf open billing page now" possible keyword rows: download invoice pdf billing

3b. Ignore-word discovery

Before building topic labels, the learner removes words that are probably structural rather than topical.

  • Connector-like words from ts.semantic.connectors(...)
  • Repeated leading tokens
  • Repeated trailing tokens

The point is to stop general frame words from dominating the learned topic label.

3c. Word families and semantic clusters

Two corpus-derived grouping signals then compete:

  • Word families: words with strong form similarity such as invoice and invoices.
  • Semantic clusters: words grouped by co-occurrence patterns from the semantic module.
// Example family signal invoice, invoices -> one family reset, resetear -> one family if the corpus supports the spelling overlap // Example semantic signal password, reset, link -> one semantic neighborhood billing, invoice, pdf -> another semantic neighborhood

Each chunk is assigned to the strongest family or cluster. The final learned intent label is built from the strongest remaining content words in that group.

The learned intent label is not a predefined taxonomy entry. It is just a compact summary of the strongest content words in that learned topic group.

Stage 4: Utterance-Type Learning

This is the part that tries to infer whether a form is query-like or statement-like without relying on punctuation or English question stems.

4a. Pattern keys

For each chunk, the learner builds structural signatures such as:

  • first two tokens
  • last two tokens
  • length bucket
"donde ver facturas abrir pagina cobros ahora" lead2 = "donde_ver" tail2 = "cobros_ahora" length = "medium"

4b. Repeated-form grouping

Chunks that share repeated openers or endings are grouped into the same utterance-type candidate. If there is no repeated pattern, the learner falls back to the chunk’s top keyword plus length bucket.

4c. Question-like scoring

Each utterance-type group gets a queryLikeScore. The score rises when the same structural frame is reused across different semantic content.

// Example query-like family donde ver facturas abrir pagina cobros ahora donde descargar recibos abrir pagina cobros ahora same frame, different content -> high queryLikeScore
// Example statement-like singleton error clave bloqueada soporte revisa caso ahora one pattern, one topic -> low queryLikeScore

If that score crosses queryLikeThreshold, the group is treated as question-like. Otherwise it stays statement-like.

This is not “question detection” in the grammar-school sense. It is closer to “does this chunk look like a reusable request/query frame in this corpus?”

Stage 5: Input Analysis

When you call intent.analyze(system, inputText, limit), the input goes through the same representation pipeline:

  1. tokenize input
  2. extract keywords against the training corpus
  3. expand related terms using semantic relationships
  4. build structural keys: lead1, lead2, tail1, tail2, length

5a. Intent classification

The expanded input vector is scored against each learned intent profile. The highest score becomes analysis.intent.label.

5b. Utterance-type classification

The same input is scored against each learned utterance profile using:

  • semantic similarity
  • leading-pattern similarity
  • trailing-pattern similarity
  • length-bucket similarity

The winning profile becomes analysis.question.type, and its learned question-likeness becomes analysis.question.isQuestion.

Final Match Scoring

Each stored chunk gets a final score against the new input using three components:

ComponentMeaning
semanticScoreWeighted overlap between input terms and chunk terms.
intentScoreHow strongly the input matches the chunk’s learned topic group.
utteranceScoreWhether the input and chunk share the same utterance-type behavior.
final score = semanticScore * semanticWeight + intentScore * intentWeight + utteranceScore * utteranceWeight

The top-ranked rows become analysis.matches.

How Responses Are Chosen

intent.responses(...) does not generate new text. It reuses neighboring corpus context.

  • If the best matching chunk has a next chunk in the same document, that next chunk becomes the response candidate.
  • If there is no next chunk, the matched chunk text itself is returned as fallback.
document: chunk 0 = "reset password account" chunk 1 = "use reset link email inbox" input matches chunk 0 response candidate = chunk 1

This is why corpus layout matters. If prompt-like material and answer-like material sit close together in the source text, response extraction works much better.

API

intent.defaultConfig()
Return the default training and scoring config.
intent.train(corpusInput, config)
Normalize documents, chunk them, learn intent profiles, and learn utterance-type profiles.
intent.analyze(system, inputText, limit)
Return learned intent, learned utterance type, question-likeness, semantic evidence, and ranked matches.
intent.responses(system, inputText, limit)
Return ranked response candidates from neighboring corpus context.

Example

intent = import("./intent.ns").intent; corpus = " como resetear clave usar enlace reset ahora como cambiar correo abrir ajustes perfil ahora donde ver facturas abrir pagina cobros ahora donde descargar recibos abrir pagina cobros ahora error clave bloqueada soporte revisa caso ahora "; system = intent.train(corpus, intent.defaultConfig()); analysis = intent.analyze(system, "como resetear correo", 3); replies = intent.responses(system, "como resetear correo", 3);

Likely behavior:

  • The input gets mapped near the como ... utterance family.
  • The learned topic will land near clave/reset/correo-like content rather than the billing group.
  • The top response candidate will usually be neighboring corpus context from one of the best matching chunks.

Practical Guidance

  • Put related prompt/answer material near each other in the corpus.
  • Use line breaks if you already know natural utterance boundaries.
  • Use a smaller chunkSize when corpus lines are dense and multi-topic.
  • Use a larger chunkStride if you want fewer overlapping chunks.
  • Expect better question-like detection when a query form repeats across several topics.
If the corpus has no repeated structural forms, the module can still learn topics, but utterance-type learning becomes weaker because there is less evidence for reusable query frames.
